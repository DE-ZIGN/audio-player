## 記録

### S1：排他モードで受け付ける形式（`ap_play --formats`、2026-11-08）

| デバイス | Windows の既定の形式 | 排他モードで受け付けた形式 |
|---|---|---|
| SSL 2 MKII USB Audio Device | 96 kHz / 32bit | 96 kHz のみ（16bit、24bit を 32bit コンテナに入れた形、32bit）。24bit パックは不可 |
| NVIDIA High Definition Audio（PL2473H） | 48 kHz / 16bit | 44.1 / 48 kHz の 16bit のみ |
| Waves SoundGrid | 44.1 kHz / 32bit 浮動小数点 | 44.1 kHz の 32bit 整数のみ |

### S1-実機：再生の結果（2026-11-08）

| 項目 | 結果 |
|---|---|
| 96 kHz / 24bit（32bit コンテナに詰め替え）、1 kHz −40 dBFS、10秒を SSL 2 MKII で再生 | 聞こえた、途切れなし（ユーザー確認）。送ったフレーム 960000 / 960000、周期 10 ms（960 フレーム）、デバイス待ちのタイムアウト 0 回 |
| ほかのアプリの音が混ざらないか | 混ざらない（ユーザー確認）。再生中は YouTube（ブラウザー）が再生を始められず、読み込み中の表示のままだった＝ブラウザーがデバイスを使えなかった |
| 音量 100% 以外の警告 | SSL 2 MKII はソフトウェア音量のため、警告ではなく「排他モードではかからない」と表示（Windows の音量 90%） |
| SSL のコントロールパネルでレートを 96 → 44.1 kHz に変えて `--formats` | 排他モードで受け付けるのが 44.1 kHz だけに変わった（16bit、24bit を 32bit コンテナに入れた形、32bit）。Windows の既定の形式も 44.1 kHz / 32bit に変わった |

### S1：分かったこと

- **SSL 2 MKII のドライバーは、コントロールパネルで設定したレートに固定する。** 排他 WASAPI からはレートを切り替えられない。この機器で曲ごとにレートを切り替えるには ASIO（1-4）が要る。WASAPI でレートが合わないときは、「SSL の設定でレートを ○○ kHz にしてください」と案内できるとよい（1-1）。
- **レートを変えると、SSL のエンドポイント ID が変わった**（96 kHz で `{181ab626-…}`、44.1 kHz で `{9ffad2c9-…}`。96 kHz に戻すと元の ID に戻った）。一覧の並び順も変わった。出力デバイスの選択を保存するときは、ID だけに頼らず、名前でも探し直す必要がある（1-1）。
- 24bit は、どのレートでも 32bit コンテナでしか受け付けない。コンテナの詰め替え（値は変えない）を入れておいたのは正しかった。

### S2：分かったこと

- **MSIX の中でも、排他 WASAPI と ASIO ドライバーの読み込みは通常の exe と同じように動く。** 配布方法（MSIX で Store）を見直す必要はない（S-判断は不要）。
- ASIO の再生（バッファーのやり取り）は、SDK を入れる 1-4 で、このパッケージを使って確かめ直す。読み込みが通れば、その先はドライバー自身のスレッドで動くので、MSIX の影響は受けにくいはず。
- **Realtek ASIO は、通常の exe でも、読み込んで解放しただけでアクセス違反でアプリごと落ちた。** ドライバーの不具合で本体が落ちないよう、1-4 では一覧づくりや試験読み込みを別プロセスで行うなどの対策を考える。
- VC++ ランタイムはパッケージの中に一緒に入れた（app-local）。本番（8-3）では、Store の VCLibs フレームワークに依存させる方法と比べて決める。

### 1-1：出力デバイスと形式の確認（2026-11-08）

### 1-2：再生キュー、ギャップレス、レートの切り替え（2026-11-08）

- **再生キュー**（`Player::setQueue`）：曲は必要になったときに開く。今の曲を再生している間に、次の曲を裏で開いておく（今は曲全体をメモリーに読む。先読みの仕組みは 1-3）。
- **ギャップレス**：次の曲が今の曲と**まったく同じ形式**なら、同じ出力のまま、今の曲の最後のフレームの直後に次の曲の最初のフレームを続ける。
- **レートの切り替え**：形式が違えば、今の曲を最後まで鳴らしてから出力を閉じ、次の曲の形式で開き直す。切り替えを「どの曲からどの曲へ」「形式」「データが途切れてから次の曲のデータを送り始めるまでの時間（無音の上限の目安）」として記録し、画面と `ap_play` に表示する。
- 次の曲をデバイスが受け付けない、または開けない場合は、そこで止めて理由を表示する。
- **自動テスト**：同じ形式の曲が続くと、出力が入力をつなげたものと1バイト残らず一致し、出力は1回しか開かれない（ギャップ 0、重なりなし）。形式が違えば開き直し、切り替えが記録される。混在、エラー、停止と再開も確かめる。
- **デバイスの通知**（`DeviceWatcher`）：出力デバイスの追加・削除・状態の変化・既定の変更を受け取る。`ap_play --watch` で表示できる。画面で使うのは 6-3。
- **要実機確認（つなぎ目の試聴）**：`build/gapless-check/` に、96 kHz・1 kHz・−40 dBFS・5 秒のファイルを3つ用意した。`1_tone_a` と `2_tone_b` は、続けると切れ目のない1本のサイン波になる。`3_click_reference` は位相を 90° ずらしたもので、`1_tone_a` に続けると継ぎ目で波形が飛ぶ（聞こえ方の比較用）。
  - 結果（SSL 2 MKII、96 kHz、`ap_play`）：`1_tone_a` → `2_tone_b` は、継ぎ目で「プツッ」と鳴らなかった（ユーザー確認）。ソフト側の記録は「ギャップレス」。比較用の `1_tone_a` → `3_click_reference` は、継ぎ目で「プツッ」と鳴った（ユーザー確認）。つまり、この条件で継ぎ目の乱れは聞き取れる。そのうえで 1 → 2 では鳴らなかったので、ギャップレスの再生は実機でも成り立っている。

### 1-3：先読み、スレッド優先度、音切れの記録（2026-11-08）

- **先読み**（`PrefetchingSource`）：専用のスレッドがファイルを先に読み、リングバッファー（既定で約2秒分）にためる。再生スレッドはそこから取り出すだけで、ディスクを待たない。再生の前にバッファーを満たしておく。目的は音切れを防ぐことで、音質向上とは謳わない。
  - 先読みが間に合わなかったときは、足りない分を無音で埋め、「ファイルの読み込みの遅れ」として回数とフレーム数を記録する（黙って隠さない）。
  - 再生中のシークは、読み込み側が新しい位置から埋め直すまでの短い間だけ無音になる（音切れには数えない）。再生していないときのシークと最初からの再生し直しは、データがそろうまで待ってから始める。
- **デバイス側の音切れ**：WASAPI では、デバイスがデータを求めてから1周期以内に渡せなかったバッファーを「デバイスへの受け渡しの遅れ」として数える。要求ごとに測るので、デバイスの時計と PC の時計のずれが長時間で積み重ならない。デバイスの応答なし（タイムアウト）も数える。
- **スレッド優先度**：再生スレッドは MMCSS「Pro Audio」。実際に効いたかを記録し、画面と `ap_play` に表示する。先読みのスレッドは通常より一段上の優先度。
- **自動テスト**：再生スレッドを止めるとデバイス側の遅れとして記録され、データは変わらない。ディスクの遅れが先読みより長いと読み込み側の音切れとして記録され、出力はちょうどその分だけ長くなる。CPU の全コアに負荷をかけた状態でも、記録と出力が食い違わない（音切れ 0 なら出力は入力と一致）。参考：負荷をかけた Debug 版では、優先度が普通のダミー出力が遅れ、15 回として記録された。
- **要実機確認**：`ap_play --stress N` で CPU に負荷をかけながら SSL 2 MKII で再生し、音切れの回数と、聞こえ方が合っているかを確かめる。
  - 結果（SSL 2 MKII、96 kHz、`1_tone_a` → `2_tone_b`、24 論理プロセッサーの PC）：負荷なし・`--stress 48` のどちらも、音切れ 0 回、MMCSS（Pro Audio）が効いた。聞こえ方も2回とも途切れなし（ユーザー確認）。
  - 検出の確認（`ap_play --inject-stall 3:50`：1 曲目の 3 秒で再生スレッドを 50 ms 止める）：3 秒のところで途切れが聞こえ（ユーザー確認）、表示は 3.0 → 3.1 秒で 0 → 1 回、集計は「デバイスへの受け渡しの遅れ 1、ファイルの読み込みの遅れ 0」。聞こえた回数と記録が一致した。
  - 途中で見つけて直した不具合：既定のバッファーの大きさが読み込みの単位で割り切れないと、先読みが満杯にならず、曲を開くたび（停止中のシークのたび）に 5 秒の待ち時間切れまで待っていた。既定の大きさで確かめるテストを足して直した。

### 1-4：ASIO 出力（2026-11-08）

- **SDK**：Steinberg ASIO SDK 2.3.4 の GPLv3 版。ホストに必要なヘッダー3つと LICENSE などを `third_party/asiosdk/` に無改変で同梱した（`VENDORED.md`）。ロゴは使わない。
- **ASIO 出力**（`AsioOutput`）：ドライバーは COM で直接作り（SDK の `asio.cpp` の全体共有の仕組みは使わない）、専用の STA スレッド（メッセージを処理するループと、隠しウィンドウ付き）からだけ呼ぶ。
  - サンプルは、ドライバーが求める形式に値を変えずに並べ替えて渡す（Int16/24/32LSB と浮動小数点はそのまま写す。Int32LSB16/24 は符号を広げる）。整数と浮動小数点の変換はしない。24bit を 32bit の形式で求められたら、WASAPI と同じコンテナの詰め替えとして扱う。
  - レートは、曲ごとにアプリからドライバーへ設定する（ASIOSetSampleRate）。
  - 音切れ：bufferSwitch が1周期より長くかかったときと、ドライバーが過負荷や同期ずれを知らせてきたときに数える。ドライバーがリセットを求めたときや、勝手にレートが変わったときは、理由を付けて止める。
- **落ちるドライバーへの対策**：ドライバーの一覧と性能の確認は、別のプロセスで読み込んで行う（`asio_probe`）。子プロセスが異常終了・応答なし・初期化失敗のときは、その旨を表示するだけで、本体は落ちない。応答がないときは、Job オブジェクトで子プロセスとそれが起動したものをまとめて終わらせる。
  - 直したこと（2026-11-10）：`ap_play --asio-list` の出力を PowerShell で途中まで読んで止めた（`Select-Object -First 12`）。すると、確認用の子プロセスが一時停止のまま残り、PowerShell も戻らなかった。原因は 2 つあった。(1) 子は一時停止で作ってから Job に入れていたので、その間に親が止められると Job に入らないまま残った。(2) 子が親の継承できるハンドルを全部受け継いでいて、シェルの出力パイプも持っていたので、シェルが子の終わりを待ち続けた。子は作った時点から Job に入れ（`PROC_THREAD_ATTRIBUTE_JOB_LIST`）、受け継ぐハンドルを結果を返すパイプだけにした（`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`）。テスト：呼び出し側の継承できるパイプを子が持たないこと（直す前の版では 1.7 秒待って失敗した）。同じ操作で 0.15 秒で戻り、子プロセスが残らないことも確かめた。一覧そのもの（8 ドライバー、0.25 秒）は前から止まっていなかった。
- **自動テスト**：偽の ASIO ドライバー（`tests/support/fake_asio_driver.h`）で、形式ごとに1バイト残らず届くこと、曲ごとのレート設定、断る理由と受け付けるレート、同じ形式の曲のギャップレス、遅れ・過負荷の記録、リセット要求、停止を確かめる。

### 1-5：DSF/DFF の読み込みと DoP 出力（2026-11-08）

- **読み込み**：DSF（1 bit/サンプルは LSB 先頭、チャンネルごとの区画）と DFF（非圧縮の DSDIFF。DST 圧縮は断る）を、内部では「MSB 先頭、1バイトずつチャンネル交互」の形にそろえる。DSF のビットの並べ替えは順番の入れ替えだけで、情報は失わない。
- **DoP**（v1.1）：24bit の PCM の上位 8bit を目印（0x05 と 0xFA をフレームごとに交互、同じフレームの全チャンネルで同じ値）、下位 16bit を DSD の 16 ビット分（時間が早いほうが上位）にする。PCM のレートは DSD のレート ÷ 16（DSD64 → 176.4 kHz、DSD128 → 352.8 kHz、DSD256 → 705.6 kHz）。出力層には普通の PCM として渡す（WASAPI 排他・ASIO・32bit コンテナへの詰め替えも、目印は崩れない）。
- **曲のつなぎ目**：各曲を偶数フレームにそろえる（足りない分は DSD の無音 0x69）。こうすると、ギャップレスでつないだときに目印の交互が途切れない。
- **安全のため、DoP は既定で送らない**。DoP に対応していない DAC では大きなノイズ（目印などが音になる）になり、DAC が対応しているかはアプリから分からないため。出力ごとに「DoP を使う」をオンにしたときだけ送る（`ap_play --dop`、アプリは今は `--allow-dop`。設定画面は 6-3）。PCM の曲と DoP の曲は、形式が同じでもつながずに開き直す（確認をすり抜けないように。DAC のモードの切り替えのためにも）。
- **画面**：入力を「DSD64（2.8224 MHz）/ 2ch（DSF）」のように DSD として表示し、処理を「なし（DoP の経路では処理をかけられません）」にする。DoP で送っている間は「DoP に対応していない DAC では、大きなノイズになります」と注意を出す。
- **自動テスト**（完了条件）：読み込みがビット単位で正しいこと（DSF のビットの向きは仕様の値で固定）、DoP の目印が交互で全チャンネル共通なこと、DSD のビットの順番、奇数の長さの埋め方、つなぎ目で目印が続くこと、シーク、DSD64/128/256 と 48 kHz 系のレート、DSF と DFF から同じ DoP が出ること、Player とダミー出力を通した並び（32bit コンテナへの詰め替え込み）、DoP を使う設定がオフのときに断ること。
- **テスト信号**：`ap_signalgen dsd` で、1 kHz のサイン波を2次のΔΣ変調した DSD を DSF/DFF で書き出せる（0 dB = 変調度 50%）。
- **要実機確認（DoP 対応の DAC が手に入ってから）**：`ap_signalgen dsd --out tone.dsf` で作ったファイルを `ap_play tone.dsf --dop`（または ASIO で `--asio N --dop`）で再生し、DAC の表示が DSD64 になるか、1 kHz の音が聞こえるかを確かめる。**SSL 2 MKII は DoP に対応していないので、DoP を送らないこと。**
- メモ：Vite の開発サーバーで画面を開くと、コンソールに「blob から worker を作ろうとして CSP に止められた」というエラーが出ることがある。こちらのコードは worker を作っていない。アプリ（WebView2）での自己テストは通る。開発サーバー側の機能に影響があるかは未確認。
- DoP の実機確認用に FiiO KA11（Type-C）を用意した（2026-11-08 注文）。表示灯は青 = PCM 48 kHz 以下、黄 = PCM 48 kHz 超、緑 = DSD（FiiO の公式サポート）。DoP の DSD64 は PCM 176.4 kHz として届くので、緑なら DSD として受けている、黄なら解釈していない（すぐ止める）。FiiO のドライバーを入れると ASIO も使え、仕様（DSD256、PCM は 384 kHz まで）からするとネイティブ DSD（フェーズ2）にも使える見込み（未確認）。
- **実機確認（2026-11-10、FiiO KA11、Windows 標準のドライバー・排他 WASAPI）**：通った。
  - `ap_play --formats --device N`：KA11 は 44.1〜384 kHz のすべてで 16bit・24bit（32bit コンテナ）・32bit を受け付け、24bit（3 バイト）と 32bit 浮動小数点は受け付けない。DSD64 の DoP は 176.4 kHz の 24bit を 32bit コンテナに詰め替えて送る。
  - 先にダミー出力で確かめた：出力のハッシュが入力と一致し、882,000 フレーム（5 秒）すべてで目印が 0x05 / 0xFA の交互（左右同じ）。
  - `ap_signalgen dsd --level -40 --seconds 15` の DSF を `ap_play --dop --device N` で再生：**表示灯は緑（DSD）**、1 kHz の澄んだ音が聞こえた（ユーザーが確認。Windows の音量 32%）。音切れ 0 回、MMCSS（Pro Audio）が効いた。1 回の受け渡しは 1764 フレーム（10 ms）。
  - DFF は自動テストで DSF と同じ DoP が出ることを確かめている（実機では DSF だけ流した）。
  - 同じ日に FiiO のドライバー（FiiO ASIO Driver 版 1552、形式 Int32LSB、44.1〜384 kHz）を入れて続けた。入れた後も WASAPI で受け付ける形式は変わらない。DSD128 もダミー出力で一致、目印の乱れなし（15 秒、5,292,000 フレーム）を確かめてから、−40 dB・15 秒の DSF を3通り流した：**WASAPI で DSD128（352.8 kHz）、ASIO で DSD64（176.4 kHz）、ASIO で DSD128（352.8 kHz）。3通りとも表示灯は緑、1 kHz の澄んだ音**（ユーザーが確認）。音切れ 0 回。ASIO では曲ごとにドライバーのレートを切り替え、バッファーはレートに合わせて変わる（176.4 kHz で 2048、352.8 kHz で 4096 フレーム。どちらも 11.6 ms）。聞こえる音量は WASAPI と ASIO で同じくらい（Windows の音量 37%。KA11 は ASIO でも Windows の音量が効いているように見えるが、測ってはいない）。
  - 未確認：DSD256 の DoP（705.6 kHz。KA11 は PCM 384 kHz までなので DoP では送れない）、ネイティブ DSD（フェーズ2）。

### 1-6：再生経路の記録（2026-11-08）

- **何を記録するか**：今の曲の経路を、各段が「実際にしたこと」だけで組み立てる（推測や判定は入れない）。エンジンの `PlayerStatus::path`（`SignalPath`）に、入力・処理・出力をまとめる。
  - **入力**：ファイルの種類（WAV / DSF / DFF）、読んだ形式、DSD を DoP で包んでいるか（DSD のレート）。
  - **処理**：フェーズ1は原音経路だけなので「なし」。段ごとの記録（音量、ReplayGain、EQ、リサンプラー、ディザ）は M3 で足す。
  - **出力**：各出力が開いたあとに自分で報告する（`AudioOutput::pathInfo()`）。
    - 共通：方式（排他 WASAPI / ASIO / ダミー出力）、デバイス名、受け取った形式、1回に送るフレーム数（周期・バッファー）、サンプルの置き方（そのまま／チャンネルごとにコピー／32bit の枠の下位に右詰め）。
    - WASAPI：イベント駆動であること、開いたときの Windows の音量（値、ミュート、デバイスの中でかかる音量か）。音量の操作がないデバイスでは何も書かない。
    - ASIO：ドライバーが返した名前と版、サンプル形式（`Int32LSB24` など）、開くときにレートを切り替えたか（切り替える前のレート）。
- **BIT-PERFECT の判定はしない**。判定と根拠の表示は 4-2・4-3 で、この記録を使って行う。
- **画面**：経路の欄に「出力の方式」と「Windows の音量」の行を足した。これまで出力デバイス名に固定で付けていた「（排他 WASAPI）」は外し、実際の方式を表示する（ASIO で再生しても「排他 WASAPI」と出ていた）。ASIO でレートを切り替えたときは、送る形式の行に「ドライバーのレートを 96 kHz → 44.1 kHz に切り替えました」と出す。出力の確認画面（SIGNAL PATH）は 6-4。
- `ap_play` も、送る形式のあとに「出力の方式」と「処理」を表示する。
- **自動テスト**（完了条件）：ダミー出力が開いている間だけ経路を報告すること、WASAPI の経路をデバイスが返した値から組み立てること（音量の扱いを含む）、WAV をそのまま送る・32bit コンテナに詰め替える・DSF を DoP で送るときの経路、偽の ASIO ドライバーで右詰めの形式（Int32LSB24）とそのままの形式（Int32LSB）、ドライバー名・版、レートの切り替えが記録されること、新しい曲の列で経路が消えること。画面の文言（方式、右詰めの説明、レートの切り替え、Windows の音量の4通り）。
- **実機での確認**（SSL 2 MKII、`ap_play`、1 kHz −40 dBFS のサイン波を3秒ずつ、音量は下げてもらった）：
  - WASAPI（SSL はコントロールパネルで 48 kHz）：48 kHz/24bit を再生。「出力の方式：排他 WASAPI（イベント駆動）・1 回に 480 フレーム（10.00 ms）」、Windows の音量は 100%（ソフトウェア音量）、送る形式は 32bit コンテナへの詰め替え。音切れ 0 回。
  - ASIO（SSL ASIO Driver 1、版 1352、最初のレート 48 kHz）：44.1 → 96 → 48 kHz の3曲を続けて再生。各曲で「ドライバーの形式 Int32LSB」と「ドライバーのレートを 48 → 44.1 / 44.1 → 96 / 96 → 48 kHz に切り替えた」が出た。切り替えは約 171 ms と約 162 ms、音切れ 0 回。
  - **分かったこと：SSL の ASIO ドライバーは、レートによってバッファーの大きさを変える**（44.1 / 48 kHz で 64 フレーム、96 kHz で 128 フレーム。どれも約 1.3〜1.5 ms）。ドライバーを読み込んだときの値ではなく、開くたびに読んだ値を記録しているので、表示もそのとおりに変わった。
  - Int32LSB はそのままの幅の形式なので「右詰め」の表示は出ない（右詰めの表示は偽のドライバーのテストでだけ確かめている）。

### 2-1：FLAC・WAV・AIFF の読み込み（2026-11-09）

- **FLAC**：libFLAC 1.5.0（BSD-3-Clause）でデコードする。C のライブラリだけを組み込み、コマンドラインのプログラム（GPL）、libFLAC++、Ogg 対応は作らない。
  - 整数のまま、元のビット数で出す。16/24/32bit 以外（12bit、20bit など）は、入る大きさの枠（16/24/32bit）の上位に詰め、「有効 20bit（24bit コンテナ）」のように記録する（WAV や WASAPI と同じ左詰め。値は変えない）。
  - スピーカーの割り当ては FLAC の決まり（1ch〜8ch）に従う。
  - **MD5 の照合**：FLAC はデコード後の音声データの MD5 を持っている。最初から最後まで途中でシークせずに読んだときだけ照合し、「一致」「不一致」を記録する。途中にシークしたら「照合できない」とし、最初に戻すと照合し直す。MD5 のないファイルは「照合用の値がない」とする。デコーダーがファイルの中の誤り（同期の喪失、CRC の不一致など）を報告したら、MD5 にかかわらず「誤りあり」とし、その数を出す。照合が合わなくても再生は止めない（結果を表示するだけ）。
  - ファイルの先頭に ID3v2 タグが付いた FLAC も開ける。
- **AIFF / AIFC**：自前で読む。AIFF はバイトの並びが逆（ビッグエンディアン）なので、サンプルごとに並びを入れ替えて渡す（値は変わらない）。AIFC は NONE・twos・in24・in32・sowt・23ni・42ni（整数）と fl32・fl64（浮動小数点）に対応し、圧縮されたもの（ulaw など）と 8bit は断る。3ch 以上はスピーカーの割り当てを「指定なし」にする（AIFF の並び順は WAV と違うため）。
- **WAV**：RF64 / BW64（4 GB を超える WAV）にも対応した。
- **開き方**：拡張子ではなく中身で形式を判断する（`detectAudioFile`）。アプリのファイル選択は .wav .flac .aif .aiff .aifc .dsf .dff。
- **画面と `ap_play`**：入力の行にファイルの種類（FLAC など）を出す。経路の欄に「ファイルの検証」の行を足し、照合の結果を出す。ギャップレスで先に進んだ曲の照合が合わなかったときは、「1 曲目は MD5 が一致しませんでした」と残す。
- **テスト信号**：`ap_signalgen` は `--out` の拡張子が `.flac` なら FLAC で書き出す（MD5 と 1 秒ごとのシーク表つき）。
- **自動テスト**（完了条件）：
  - FLAC：16/24/32bit × 44.1〜384 kHz で、デコード結果がエンコードした PCM と1バイト残らず一致し、MD5 が一致する。12bit・20bit の左詰め、1/2/6/8ch の割り当て、MD5 の書き換えを「不一致」と報告すること、壊したフレームを「誤りあり」と報告すること、MD5 なし、シーク（正確な位置、照合できない → 最初に戻すと照合）、ID3v2 付き、FLAC でないファイルを断ること。Player を通したとき、先に進んだ曲の照合結果が残ること。
  - AIFF / AIFC：16/24/32bit と 20bit、AIFC の型ごとの並び、SSND のオフセットや知らないチャンク、80bit のサンプルレート（8 kHz〜768 kHz）、シーク、途中で切れたファイル、断るべきファイル。
  - RF64 / BW64、中身による形式の判断（拡張子をわざと違えたファイル）。
  - **受け入れ基準（CLAUDE.md 5章）**：FLAC 入力（16/24/32bit × 44.1〜384 kHz × 3種類の信号）でダミー出力のハッシュが元の PCM と一致する。AIFF 入力も、並びを入れ替えた結果が元の PCM と一致する。
- **手持ちの音源での確認**（2026-11-09。ユーザーが用意した8ファイル。音源はリポジトリの外に出さないよう、`.git/info/exclude` で除外した）：
  - ダミー出力（音は出さない）で全ファイルを最後まで読み、**8ファイルすべてで出力のハッシュが入力と一致**した。FLAC：44.1 kHz/16bit（約7分、MD5 一致）、48 kHz/24bit（約6分、MD5 なし＝作ったソフトが記録していない）、192 kHz/24bit（MD5 一致）。AIFF：44.1 kHz/16bit、96 kHz/24bit。WAV：44.1 kHz/16bit、192 kHz/24bit、192 kHz/32bit。
  - AIFF の2つは、別に書いた簡単な読み込みプログラム（Python）の結果とも1バイト残らず一致した。
  - 同じ曲の組（AIF と WAV、FLAC と WAV）は出力が一致しなかったが、サンプルを比べると WAV のほうがどちらも約 13 dB 大きく、始まりの位置もずれていた。FLAC は MD5、AIFF は別の読み込みプログラムで正しく読めていることを確かめてあるので、ファイルそのものが別の設定で書き出されたものと判断した。
  - 実機（SSL 2 MKII、ASIO、音量は下げてもらった）：AIFF 44.1 kHz/16bit → FLAC 192 kHz/24bit → AIFF 96 kHz/24bit → WAV 192 kHz/32bit を続けて再生。4曲とも鳴り、SSL のレート表示も曲ごとに変わった（ユーザー確認）。切り替えは約 182 / 159 / 159 ms、音切れ 0 回。192 kHz では ASIO のバッファーが 256 フレームになった（約 1.3 ms。レートでバッファーの大きさを変える動きは 1-6 と同じ）。
- **途中で見つけて直した不具合（`ap_play --dummy`）**：最初は8ファイル中7ファイルで「不一致」になった。デコーダーの問題ではなく（FLAC の MD5 は一致していた）、ダミー出力がデバイスと違って「できるだけ速く」データを受け取るため、約2秒分の先読みを追い越し、先読みが足りない分を無音で埋めていた（デバイスのための正しい動きで、音切れとして記録されていた）。これまで確かめたファイルは1秒以下で、先読みに収まっていたので表に出なかった。`--dummy` のときは先読みを使わずファイルを直接読むようにし、無音で埋めたときは不一致の理由を表示するようにした。自動テストの受け入れ基準は先読みを通さないので、影響はない。

### 2-2：ALAC（2026-11-09）

- **デコーダー**：Apple の公開版（macosforge/alac、Apache 2.0）のデコーダーを `third_party/alac/` に同梱した。
  - **公開版は 2011 年から直されておらず**、同じコードを使った MediaTek・Qualcomm のデコーダーで、細工した音声ファイルでメモリーを壊せる脆弱性が見つかっている（Check Point「ALHACK」、CVE-2021-0674 / 0675 / 30351）。原因は、ファイルの中の値を確かめずに使っていること。
  - このプレイヤーはどこから来たファイルでも開くので、**値を使う前にすべて確かめる変更を 10 か所入れた**（ファイルの先頭の設定、フレームごとのサンプル数、各チャンネルのビット数、パケットの終わりを超えて読まないこと、など）。一覧と元のファイルのハッシュは `third_party/alac/VENDORED.md`。手を入れたのは2ファイルだけで、ほかは上流と1バイトも違わない。
  - 上流の `codec/` には Apple Public Source License の本文も置かれているが、使うファイルはどれも Apache 2.0 のヘッダーを持ち、それを参照していないので同梱していない。
  - MSVC の x64 では、上流のバイト順の判定が働かない（`__x86_64__` は GCC の記号）。ソースは変えず、`TARGET_OS_WIN32` を定義して正しい側を選ばせている。
- **入れ物**：MP4（.m4a）を自前で読む（`mp4_reader`）。最初の音声トラックの、各パケットの位置・大きさ・フレーム数、コーデックの設定、編集リスト（最初の空でない編集：先頭を飛ばす量と長さ）を取り出す。大きさや数はすべて、入っている箱とファイルの大きさで確かめる。.m4a でも中身が AAC のものは「2-4 で対応」と理由を付けて断る。.caf は対応しない（使う人が少ないため。必要なら後で）。
- **出力**：整数のまま、元のビット数で出す。20bit は 24bit の枠の上位に詰める（FLAC と同じ）。3ch 以上はスピーカーの割り当てを「指定なし」にする（ALAC の並びは中央が先頭で、WAV と違う）。照合用の値はないので、ファイルの検証は「照合用の値なし」。デコーダーが断ったパケットは同じ長さの無音にし、「誤りあり」として数える。
- **分かったこと：Windows の ALAC エンコーダーは、曲の本当の長さを残さない**。最後のパケットを無音で 4096 フレームまで埋め、表にも「全部 4096 フレーム」と書く（トラックの長さも同じ）。そのため Windows で作った ALAC は、最大で約 0.09 秒（44.1 kHz）の無音が曲の終わりに付き、ギャップレスにはならない。ファイルにそう入っているので、このプレイヤーも Windows のデコーダーと同じ長さで再生する。Apple の道具で作ったファイルは、最後のパケットに本当のフレーム数が入っているので、ちょうどの長さで再生する。
- **テスト用のファイル**は2通りで作った：
  - Apple のエンコーダー（テスト専用。同じリポジトリの、手を入れていないもの）と、テスト用の小さな MP4 書き出し。Apple の道具と同じく、最後のパケットに本当の長さが入る。16/20/24/32bit、44.1〜384 kHz、1〜8ch。
  - Windows の ALAC エンコーダー（Apple のコードとは別の実装）。16/24/32bit、44.1〜192 kHz（352.8 / 384 kHz は受け付けなかった）。
- **自動テスト**（完了条件）：
  - デコード結果が元の PCM と1バイト残らず一致し、長さもちょうど（16/20/24/32bit × 44.1〜384 kHz）。圧縮できない信号（そのまま格納する経路）、1〜8ch、編集リスト、シーク。
  - Windows で作ったファイル：埋められた無音までを含めて、Windows のデコーダーの結果と1バイト残らず一致。Apple のエンコーダーで作ったファイルも、Windows のデコーダーの結果と一致。

  - **AddressSanitizer**（メモリーの誤った読み書きを見つける仕組み）を入れたビルド（`vs2022-asan`）でも、全テスト（182 件）が通った。

- 気づいた小さな問題（未対応）：`ap_play` のエラーの1行で、日本語のフォルダー名が文字化けする。エンジンのエラー文（英語、ログ用）がパスを Windows の文字コードで入れていて、`ap_play` は UTF-8 で表示しているため。ファイルを開くことには影響しない。エラー文のパスを UTF-8 にそろえるときに直す。

### 2-3：MP3（2026-11-09）

- **デコーダー**：mpg123 1.33.7（LGPL 2.1）を DLL（`mpg123.dll`）として組み込んだ。公式のソース配布をハッシュで固定し、mpg123 の CMake でデコードのライブラリだけを作る。アセンブラーを使わない C だけのデコーダーにした（どの CPU でも同じ結果になるので、テストで値を確かめられる）。DLL はアプリ・`ap_play`・テストの exe の隣にビルドのたびに置き、MSIX の試作パッケージにも入れた。
- **浮動小数点のまま**（CLAUDE.md：非可逆は浮動小数点でデコード）：mpg123 の計算と出力はどちらも 32bit 浮動小数点。整数に丸めないので、デコードした波形が 1.0（0 dBFS）を超えるところもそのまま残る（クリップしない）。64bit で計算しても違いを測れないので、そうはしていない。
- **実機での再生は M3 で**（ユーザーと相談して決めた）：手元のデバイスは、どれも排他モードと ASIO では整数の形式しか受け付けない。浮動小数点をディザをかけて整数にするのは処理経路（M3 の 3-1・3-2）の仕事なので、それまでは整数しか受け付けないデバイスでは「浮動小数点の形式に対応していません。処理経路ができるまで再生できません（勝手に変換はしません）」と理由を出して断る。浮動小数点を受け付けるデバイスなら、今でもそのまま送れる。`ap_play --formats` に「32bit 浮動小数点」の列を足した（KA11 などで確かめるため）。
- **ギャップレス**：LAME タグに書かれたエンコーダーの遅延と末尾の埋め草を mpg123 が取り除く。開くときにファイルを読み通して、長さをちょうどに決める。LAME タグのない MP3 は、何を取り除けばよいかがファイルに書かれていないので、元の音より長くなる（テストで確かめた）。
- **シーク**：位置はちょうど。値は、頭から読んだときと浮動小数点の丸めの範囲で一致する（最大 1.2×10⁻⁷、約 −138 dBFS、24bit の1段ぶん）。1ビット単位で一致しないのは、mpg123 の合成フィルターが書き込む輪状のバッファーの開始位置がフレームごとに進み、シークのあとは別の位置から始まるため、同じ足し算の順番が変わって最後の桁の丸めが変わるから。位置がずれていれば、差は信号そのものの大きさになる。
- **テスト用のファイル**：LAME 3.100（LGPL）をテスト専用にビルドして作った（配布物には含まない）。LAME タグを書くエンコーダーが要るため。
- **自動テスト**（完了条件）：
  - 長さがちょうどで、位置がずれない（MPEG-1・2・2.5 の 8 通りのサンプルレート × モノラル・ステレオ、VBR）。
  - **Windows の MP3 デコーダー（別の実装）との差**：3通りのレート × CBR 128 / CBR 320 / VBR × 3種類の信号（音楽ふう・0 dBFS 近くの矩形波・−60 dBFS のサイン波）の27通りで、差の RMS が −94〜−99 dBFS、最大が −89.8〜−90.4 dBFS。基準は「RMS −90 dBFS 未満、最大 −70 dBFS 未満」にした。差の最大がほぼちょうど −90.3 dBFS（1/32768）なのは、Windows のデコーダーが内部で 16bit に丸めているためと見られる（比べているのは主に相手側の分解能）。
  - **クリップしない**：0 dBFS 近くの矩形波で、こちらの出力には 1.0 を超える値が残る。Windows のデコーダーは最大がちょうど 1.0000 で、クリップしている（比べるときは、こちらの値を同じく ±1.0 に収めて比べた）。
  - ギャップレス：1本の信号を2つに分けてそれぞれ MP3 にし、続けて再生すると、長さが元とちょうど同じで、後ろの曲の始まりもずれない。
  - 整数しか受け付けない出力では、理由（浮動小数点）を付けて断り、変換しない。
  - 中身による形式の判断（ID3v2 付きも）、日本語のファイル名、壊れたファイル・MP3 でないファイルで落ちないこと。AddressSanitizer のビルドでも通した。
  - **受け入れ基準（CLAUDE.md 5章）**：「非可逆デコード：リファレンスデコーダーとの差が許容範囲内で、クリップがない」を、上の27通りで自動テストにした（`tests/acceptance/lossy_test.cpp`）。
- **手持ちの MP3 での確認**（2026-11-09、ユーザーが用意した3つ。音は出さない）：

  | ファイル | 作ったもの | 遅延の情報 | 長さ（元の WAV は 486,620 フレーム） | Windows のデコーダーとの差 |
  |---|---|---|---|---|
  | convertio .mp3 | FFmpeg（LAME、オンライン変換） | あり（Xing/LAME） | **486,620（ちょうど）**、元の WAV とのずれ 0 フレーム、SNR 31.9 dB | RMS −95.8 dBFS、最大 −90.3 dBFS |
  | Nuendo 128 kbps | Nuendo の書き出し | なし | 489,600（2,980 長い）、1,201 フレーム遅れて始まる | RMS −95.3 dBFS、最大 −90.3 dBFS |

  - Nuendo の MP3 は遅延の情報を書かないので、曲の頭に約 27 ms の無音が付き、長さも合わない（ファイルにそう入っている。Windows のデコーダーでも同じく長い）。
  - Nuendo の MP3 は、音量が同じ時に書き出した AIF と同じ（WAV より約 13.8 dB 小さい）だが、位置を合わせても AIF との相関は 0.83 しかなく、同じ音の MP3 とは言えなかった（320 kbps なら 0.999 程度になるはず）。書き出しの設定か処理が違うものと見られる。デコーダーについては、Windows のデコーダーとの差がほかのファイルと同じ水準なので、問題はない。
  - 実際のファイルを Windows のデコーダーと元の WAV に照らす確認は、テスト（`[.probe]`、環境変数 `AP_PROBE_IN` と `AP_PROBE_WAV`）として残した。
- **要実機確認**：実際に鳴らすのは、M3 で処理経路（ディザをかけて整数にする）ができてから、SSL 2 MKII で。
- 対象外：iTunes で作った MP3 の iTunSMPB（もう1つの長さの記録方法）。mpg123 は読まず、2-4 でも AAC だけに使った。iTunes で作った MP3 が手に入ったら、必要か確かめる。

### 2-4：AAC（2026-11-09）

- **デコーダー**：CLAUDE.md のとおり AAC のデコーダーは同梱せず、Windows の AAC デコーダー（Media Foundation の変換部品）を呼ぶ。.m4a は 2-2 の自前の読み込みで開き、パケットを1つずつデコーダーに直接渡す（曲の頭と終わりの削り方、シークをこちらで正確に決めるため）。出力は 32bit 浮動小数点（MP3 と同じ。実機での再生は M3 で）。
- **ギャップレス**：エンコーダーが頭に足したサンプル（priming）と末尾の埋め草を取り除く。編集リスト（elst）があればそれを、なければ iTunes の iTunSMPB を使う。どちらもなければ、何を取り除けばよいかがファイルに書かれていないので、デコードしたものを全部再生する。HE-AAC のように出力のレートが時間の単位の倍数になる場合も、その倍率で数え直す。
- **シーク**：AAC のフレームは前のフレームと重なっているので、目的の位置の2パケット前からデコードし直し、目的の位置より前の出力は捨てる。
- **分かったこと**：
  - **Windows の AAC エンコーダーは、elst も iTunSMPB も書かない**。ただし、Windows のエンコーダーで作って Windows のデコーダーで戻すと、priming は 0 フレームで、最後に 1 パケット未満の埋め草（543〜935 フレーム）が付くだけだった。
  - **Windows の AAC デコーダーはクリップしない**：0 dBFS 近くの矩形波で、1.0 を超える値がそのまま残った（最大 1.26）。MP3 のデコーダー（16bit に丸め、1.0 で切る）とは違う。
  - **Windows の AAC デコーダーは、壊れたデータを報告しない**：パケットを壊した 120 通りで、デコーダーからの誤りの報告は 0 回だった（誤りを黙って補うと見られる）。落ちることはなく、AddressSanitizer のビルドでも通った。
- **自動テスト**（完了条件）：
  - Windows のエンコーダーで作ったファイル（elst も iTunSMPB もない）：デコードしたもの全部を再生する（埋め草の分だけ長い）。
  - elst と iTunSMPB で頭を 0・1・1024・2112 フレーム、終わりを 777 フレーム削る指定をしたファイルで、削らずにデコードしたものの指定の範囲と1ビット違わず一致すること。priming を測った値で書き込んだファイルでは、長さが元とちょうど同じで、ずれが 0 になること。
  - Windows 自身のファイル読み取り（Media Foundation のソースリーダー）と、長さ・位置・値が完全に一致すること（デコーダーは同じなので、こちらの入れ物の読み方とパケットの渡し方の確認）。
  - シーク：位置がちょうどで、値も1ビット違わず一致（差 0）。
  - ギャップレス：1本の信号を2つに分けたファイルを続けて再生すると、長さが元と同じで、後ろの曲の始まりもずれない。
  - 整数しか受け付けない出力では、浮動小数点の理由を付けて断る。
- **「リファレンスデコーダーとの差」について**：AAC は CLAUDE.md の決まりで Windows のデコーダーそのものを使うので、別の実装との差は測っていない。必要なら、テスト専用に別のデコーダー（faad2 など）を入れて比べられる。
- **要実機確認**：
  - **Apple（iTunes / ミュージック）や FFmpeg で作った AAC**（iTunSMPB の priming は 2112、FFmpeg の elst は 1024 が普通）を、元の WAV と比べて、長さがちょうどで、ずれが 0 になるかを確かめる。Windows のデコーダーの出力の始まりが、これらのエンコーダーの priming の数え方と合っているかは、この確認でしか分からない。
  - 実際に鳴らすのは、M3 で処理経路ができてから。
- **確認（2026-11-10）**：
  - プローブ（`ap_engine_signal_tests "Probe: a real AAC against Windows' reader and its source WAV"`、`AP_PROBE_IN` に .m4a、`AP_PROBE_WAV` に元の 16bit WAV）を足した。
  - **iTunes で作った AAC**（`16-441 -AAC - iTunes.m4a`、元は 11 秒の 16bit WAV）：edit list なし、iTunSMPB はプライミング 2112・余り 740・元の長さ 486,620 フレーム。iTunSMPB で削った結果は 486,620 フレームで、**元の WAV と長さの差 0、ずれ 0**。SN 比 31.7 dB（2-3 の MP3 の 31.9 dB と同じくらい）、ピーク −3.07 dBFS、デコードのエラー 0。Windows のデコーダーの出力の始まりが Apple の priming の数え方と合っていることが分かった。Windows 自身のファイル読み込み（Media Foundation）は iTunSMPB を使わないので、頭に 2112 フレーム多く出る（こちらの読み込みとのずれ 2112）。
  - 同じファイルを KA11 で再生（3-2 の処理経路で 32bit 整数・TPDF ディザ）：普通に聞こえた（ユーザーが確認）。音切れ 0 回。
  - FFmpeg で作ったものは ADTS（`.aac`、MP4 に入っていない）だった。ADTS には頭と末尾を削る情報を入れる場所がないので、どのプレーヤーでも正確な長さにはできない。今は .m4a だけに対応（`.aac` は読めないと表示する）。FFmpeg 製は `.m4a` で書き出したもの（`ffmpeg -i in.wav -c:a aac out.m4a`、edit list でプライミング 1024 を書く）で確かめる（U）。ADTS の .aac を読めるようにするかは、必要になったら決める。
  - **FFmpeg で作った AAC**（`16-441-AAC用-ffmepeg_v2.m4a`、convertio.co で変換。ファイルに `Lavf58.76.100`・`Lavc58.134.100` = FFmpeg 4.4 の記録があり、サイト特有ではなく FFmpeg の既定の動き）：edit list でプライミング 1024。頭のずれは 0 だったが、**長さが 21 フレーム短かった**。原因：FFmpeg は全体の時間の単位（mvhd）を既定で 1/1000 秒にし、edit list の長さを切り捨てて書く（11,034.47 ms → 11,034 ms = 486,599 フレーム）。一方、最後のパケットの時間の表（stts）には残りの正確なフレーム数（220）が入っている。
  - **修正**：edit list の長さが、ストリームの残り（パケットの表から計算した長さ）を全体の時間の単位で表したもの（切り捨て・四捨五入のどちらか）と一致するときは、ストリームの残りを正確な長さとして使う。一致しない（1 単位以上短い）ときは、今までどおり edit list の長さで切る。全体の時間の単位が音声と同じファイル（Apple、テスト用の muxer）では、今までと同じ結果になる。弱点：エンコーダーの末尾の余りが 1 単位（1 ms）未満のときは、その余りも鳴らす。
  - 修正後、FFmpeg の AAC は 486,620 フレーム（**元の WAV と長さの差 0、ずれ 0**、SN 比 19.1 dB。iTunes より低いのは FFmpeg 内蔵のエンコーダーの質の差で、デコーダーは同じ）。iTunes の AAC は変わらず差 0・ずれ 0。
  - 自動テスト：テスト用の muxer に、全体の時間の単位（edit list の長さを切り捨てて書く）と、FFmpeg と同じく最後のパケットの表に残りのフレーム数を書く書き出し（`rewriteAacM4aLikeFfmpeg`）を足した。44.1・48 kHz、末尾の余り 1・300・1000 フレームで、長さがちょうど、値は削らない復号とビット単位で一致。edit list が本当に 100 ms 短いときは延ばさない。修正前のコードでは、実ファイルと同じく末尾が欠けて失敗することを確かめた。

### 3-1：64bit の処理経路と完全バイパスの判定（2026-11-10）

- **処理の段**（`ProcessingStage`）：64bit 浮動小数点（フルスケール = ±1.0、インターリーブ）を、その場で書き換える。「今は何もしない状態か」（`isIdentity()`、例：音量 100%）を返す。処理の列（`ProcessingChain`）は段を決まった順に並べ、何もしない段は飛ばす。実際の段（音量、ReplayGain、EQ など）は 3-2 以降で入れる。
- **完全バイパス**：出力を開くときに、すべての段が何もしない状態なら、今までの一本道（原音経路）をそのまま使う。処理のコードは1行も通らない。DoP の曲は、段が有効でも処理しない（Player の曲の列からも DoP かどうかが伝わるようにした）。
- **変換**：16/24/32bit の整数（コンテナの幅で読み、2^(コンテナのビット数−1) で割る）と 32/64bit の浮動小数点を 64bit 浮動小数点にし、出力の形式に戻す。整数は有効ビット数で最も近い値に丸め（ちょうど中間は偶数へ）、範囲の外は端の値にそろえて数える。コンテナの下位ビットは 0。浮動小数点の出力はそろえない（範囲の外は数えるだけ）。NaN は 0 にする。**ディザはまだかけない**（3-2 で、量子化の前に入れる）。
- **処理経路の出力形式**（ユーザーと決めた）：レートとチャンネル数は曲のまま。サンプル形式は、デバイスが受け付ける中でいちばん細かいもの：32bit 整数 → 24bit（32bit コンテナ）→ 24bit → 16bit → 32bit 浮動小数点（整数を受け付けないデバイスだけ）。KA11 と SSL 2 MKII は 32bit 整数になる。
- **置き場所**：再生スレッド（ASIO ではドライバーのスレッド）で、先読みの後に処理する（音量の変更が先読みの分だけ遅れないように）。処理の間だけ FTZ/DAZ を有効にし、終わったら元に戻す（ドライバーのスレッドの設定を変えたままにしないため）。
- **経路の記録**：`SignalPath::processing` と、出力を開いたときに有効だった段の名前（`processingStages`）を記録する。範囲の外に出たサンプルの数を `PlaybackReport::overs` に数える（画面に出すのは 3-5 のリミッターの記録と一緒に）。
- **自動テスト**（完了条件）：
  - 受け入れ：何もしない段だけの列で、バイパスが成立し、出力が原音経路とバイト単位で一致する（16/24/32bit × 44.1〜384 kHz × ビットパターン・ISP 信号・1 kHz −90 dBFS の 72 通り）。同じ入力を処理経路に強制的に通して同じ形式で出しても一致する（変換だけでは値が変わらない）。
  - 単体：整数（16/24/32bit、24bit・16bit を広いコンテナに入れたもの）と浮動小数点が往復で変わらないこと、丸めと範囲の外の扱い、出力形式の選び方、処理経路でもギャップレスでつながること、段が有効なら値が変わること、FTZ/DAZ が処理中だけ効くこと、DoP を処理しないこと、Player の経路の記録。
- **申し送り（3-2）**：
  - 再生中にバイパスかどうかが変わったとき（例：原音モードで音量を 100% から下げた）は、今の位置で出力を開き直す（ユーザーと決めた。約 25 ms と DAC の合わせ直しの間だけ途切れる。途切れない切り替えは 3-7）。音量の段と一緒に作る。
  - 整数しか受け付けないデバイスで MP3・AAC を鳴らせるのは、ディザをかけて量子化する 3-2 から。3-1 の時点では、処理経路で浮動小数点を整数にする段は実際には動かない（実際の段がまだないため）。

### 3-2：デジタル音量と TPDF ディザ（2026-11-10）

- **TPDF ディザ**：整数に量子化するときだけ、±1 LSB（出力の有効ビット数での LSB）の三角分布の値を足してから丸める。浮動小数点の出力にはかけない。範囲の外のサンプルは、ディザを足す前の値で数える（フルスケール付近でディザのせいで数えないように）。乱数は xoshiro256**（パブリックドメイン）で、出力を開くたびに同じ種から始める（同じ入力なら同じ出力。テストを再現できる）。ノイズシェーピングはしない。
- **音量の段**（`VolumeStage`）：0 dB 以下（上げることはできない。上げるとクリップするため。ヘッドルームは 3-5 の ISP セーフの仕事）。−∞ でミュート。変えたときは 10 ms で直線的に移る（波形に段差を作らない）。0 dB で、移り終わったときだけ「何もしない」状態になる。出力を開いたときは移らずに、その時点の音量から始める。
- **再生中の切り替え**（3-1 でユーザーと決めた）：処理経路が要るかどうかが変わったら（音量を 100% から下げた、100% に戻して移り終わった）、今の位置で出力を開き直す。曲の切り替えと同じ記録（`TransitionKind::ProcessingChanged`、切り替えにかかった時間）を残す。フレームの欠けも重なりもない（テストで確認）。DoP の曲は切り替えない。
- **浮動小数点の曲を整数のデバイスで鳴らす**：MP3・AAC など浮動小数点の曲を、浮動小数点を受け付けないデバイスで鳴らすときは、音量 100% でも処理経路（段なし、TPDF ディザ）で整数にする（非可逆の曲には整数の原音がないため）。経路の記録には `processingRequired` を立てる。整数の曲をデバイスが受け付けない場合は、今までどおり変換せずに理由を出す（浮動小数点だけのデバイスなど）。2-3・2-4 で「M3 まで再生できない」としていたものが、これで鳴らせる。
- **判定の共通化**：直接送るか処理経路かの判定を `planPlayback()` にまとめ、`play()` と `ap_play --check` が同じものを使う。
- **表示**：経路の記録に `processingStages`・`processingRequired`・`dither` を足し、アプリ（ブリッジと画面の文言）と `ap_play` に出す（例：「あり（64bit 浮動小数点の処理経路：デジタル音量、TPDF ディザ）」）。`ap_play` に `--volume DB` と `--volume-at 秒:DB` を足した。
- **自動テスト**（完了条件）：
  - 100% で完全バイパス：受け入れテスト（3-1 の 72 通り）の処理の列に、0 dB の音量の段を入れても原音経路と一致する。Player でも音量 100% はビットパーフェクト。
  - ディザの統計：ディザの値が (−1, 1) の三角分布（分散 1/6、各区間の割合）。ディザをかけた量子化誤差は、入力が LSB のどこにあっても平均 0・分散 1/4 LSB²（ディザなしでは入力によって変わることも確かめる）。誤差は 1.5 LSB 以内。フルスケールでディザのせいで範囲の外と数えない。24bit（32bit コンテナ）では 24bit の LSB でかかり、下位 8 bit は 0。浮動小数点の出力にはかけない。同じ種なら同じ値。
  - 音量：0 dB だけ「何もしない」、出力を開いたときはその音量から、10 ms で直線的に移る（単調で、段差は1歩分以内、最後はちょうど目標値）、ミュート、0 dB に戻ったら移り終わってから「何もしない」。
  - Player：100% → −6 dB → 100% で「原音（16bit）→ 処理（32bit）→ 原音（16bit）」と開き直し、どのフレームも1回ずつ出る。浮動小数点の曲は、整数だけのデバイスでは 100% でも処理経路（ディザあり）、浮動小数点を受け付けるデバイスではビットパーフェクト。整数の曲でレートが合わないときは今までどおり断る。DoP の曲は音量を変えても切り替えない。
  - 3-1 のテストのうち「処理経路でも値が変わらない」ことを確かめていたものは、浮動小数点の出力（量子化しないのでディザもない）で完全一致、整数の出力では 1 LSB 以内、に書き換えた。MP3・AAC の「整数だけのデバイスでは断る」テストは「ディザをかけて整数にして鳴らす」に書き換えた。
- **要実機確認**（KA11 で、音量を下げてから）：
  1. MP3・AAC（`テスト用音源`）を `ap_play FILE --device N` で再生し、「処理：あり（…浮動小数点の曲を整数にする…TPDF ディザ）」と出て、普通に聞こえること（2-3・2-4 の実機での再生）。
  2. WAV か FLAC を `ap_play FILE --device N --volume-at 5:-12 --volume-at 10:0` で再生し、5 秒で音量が下がり（経路の切り替えの表示）、10 秒で元に戻る（原音経路に戻る表示）こと。切り替えのときに短い無音が入るのは仕様（約 25 ms と DAC がレートに合わせ直す時間）。途切れずに切り替えるのは 3-7。
- **実機確認（2026-11-10、FiiO KA11、排他 WASAPI）**：
  - MP3（`16-441-出力-Stereo-Out-convertio.mp3`、11 秒）：44.1 kHz の 32bit 整数で送り、「処理：あり（…浮動小数点の曲を整数にする…TPDF ディザ）」。普通に聞こえた（ユーザーが確認）。音切れ 0 回。2-3 の実機での再生はこれで完了。
  - WAV（16bit、11 秒）を `--volume-at 4:-12 --volume-at 8:0` で：0〜4 秒は原音経路（16bit そのまま）、4 秒で処理経路（32bit、デジタル音量・TPDF ディザ）、8 秒で原音経路に戻った。切り替えでデータが途切れたのは約 24 ms と 25 ms。音量の変化は聞こえたとおりで、切り替えのところも気にならなかった（ユーザーが確認）。音切れ 0 回。
  - AAC は `テスト用音源` になかった（.m4a はすべて ALAC）。iTunes で作った AAC を用意してもらい、元の WAV との比較（2-4 の残り）と一緒に確かめる。

### 3-3：True Peak 解析（2026-11-10）

- **方式**：8 倍オーバーサンプリング（どのレートでも 8 倍）。窓付き sinc（Kaiser β = 8、1 位相 48 タップ、全長 385）のポリフェーズ補間で、サンプルの間の 7 点を求めて絶対値の最大を取る。遮断は入力のナイキスト周波数ちょうどで、元のサンプル位置ではちょうど元の値を通す（ナイキストフィルター）。だから True Peak はサンプルピークより小さくならない。最後のサンプルの後ろも補間する（`finish()` で 0 が続くとして 49 サンプル分）。チャンネルごとに、サンプルピーク・True Peak・True Peak の位置（サンプルの間の位置まで）を持つ。
- **8 倍の限界**：サイン波は、山の頂上が 8 倍の格子の間に来ると低く出る。最大で 1 − cos(π f / 8 fs)：fs/4 で 0.042 dB、0.45 fs で 0.14 dB。ISP 信号（fs/4、45 度）は頂上が格子の上に来るのでちょうど測れる。
- **ファイル全体の解析**：`analyzePeaks(PcmSource&)`（DoP は対象外）。`ap_play --analyze FILE...` で表示する。取り込み時の解析（ライブラリへの保存、アルバムの True Peak）は M5、ISP セーフの計算は 3-5、メーターの画面は 4-4。
- **自動テスト**（完了条件）：
  - 受け入れ：`ap_signalgen` と同じ ISP 信号（0 dBFS）を 16/24/32bit × 44.1〜384 kHz の WAV に書き、読んで測る。続いている部分は **+3.01 dB ± 0.02 dB**（サンプルピークに対して）。ファイル全体は、急に始まって急に終わる端で帯域制限した波形が本当に行き過ぎるので、それ以上（実測 +3.10 dB）。端の行き過ぎは本物の値なので、メーターでは除かない（ISP セーフは、全体の値から下げる量を決めるので安全側）。
  - 単体：ISP 信号（フェードあり）が +3.01 dB ± 0.02 dB（A = 1、0.5、16bit の最大値）。急に始まると行き過ぎる。True Peak はサンプルピーク以上。fs/4 までのサイン波は 0.05 dB 以内で低く出て、高くは出ない。0.45 fs までは 0.15 dB 以内。帯域制限した乱数信号で、長い sinc（±4000 サンプル、16 倍の格子）で直接補間した値と 0.1 dB 以内（高くは出ない）。小分けに処理しても同じ値。`finish()` で最後のサンプルの後ろまで測る。チャンネル別、無音は −∞ dB、`reset()`。ピークの位置（1 サンプルのインパルスはそのサンプル、2 サンプル続けば真ん中）。
- **実ファイル**（`テスト用音源`）：解析の速さは 44.1 kHz で再生の約 130 倍、192 kHz で約 30 倍（Release）。
  - Apple Music Live の 11 曲（ALAC 48 kHz / 24bit）：どれも約 −1 dBTP、サンプルピークとほぼ同じ（−1 dBTP に収めたマスタリングに見える）。
  - `01 - Immortal.flac`（44.1 kHz / 16bit）：サンプルピーク −0.13 dBFS、**True Peak +2.96 dBTP**（4:29.042）。その位置の値を見ると、隣り合うサンプルが −32295 と +32295 の間を行き来する（左右同じ、フルスケール近くの矩形のような波形）。端の行き過ぎではなく、曲の中にある本物のインターサンプルピーク。原音モードでの ISP 警告と ISP セーフ（3-5）が要る例。
  - `01 - King.flac`（48 kHz / 24bit）：+0.26 dBTP（サンプルピーク −0.10 dBFS）。
  - 11 秒の書き出し（16bit / 44.1 kHz の WAV・ALAC・AAC・MP3）：−2.7〜−3.1 dBTP 前後で、サンプルピークより 0〜0.3 dB 高い。

### 3-4：ReplayGain 2.0（2026-11-10）

- **依存**：libebur128 1.2.6（MIT。同梱の `queue.h` は BSD-3-Clause）。リリースのタグのソース（25,890 バイト、SHA-256 固定）から `ebur128.c` の1ファイルだけを静的ライブラリにする（配布物の CMake は使わない）。THIRD_PARTY_NOTICES に追記した。
- **ラウドネス**：ITU-R BS.1770 の統合ラウドネス（ゲート：絶対 −70 LUFS、相対 −10 LU）。モノラルはデュアルモノとして測る（モノラルの曲は両方のスピーカーで鳴るため。ReplayGain 2.0 と同じ扱い）。アルバムは全曲のブロックをまとめてゲートをかける（曲の値の平均ではない）。ピークは libebur128 のものを使わず、3-3 の True Peak を同じ読み込みで測る（`analyzeTrack`、`analyzeAlbum`）。
- **ReplayGain**：ゲイン = −18 LUFS − ラウドネス（無音は 0 dB）。**上限（ユーザーと決めた）**：ゲインをかけても True Peak が 0 dBTP を超えないように、ゲインは −True Peak（dB）までに抑える。さらに 0.5 dB の余裕を取るのは 3-5 の ISP セーフ。固定の最大値（+○ dB まで）は設けない。
- **再生での適用**：処理経路の最初の段（`ReplayGainStage`、オフ／トラック／アルバム。アルバムの値がない曲はトラックの値）。値がない曲、オフ、ちょうど 0 dB は「何もしない」。値は曲の列の項目（`QueueItem::replayGain`）に持たせる（今は再生する側が解析して渡す。ライブラリの DB から入れるのは M5）。
- **曲の境目で正確に切り替える**：Player の曲の列が、1 回の読み込みの中で次の曲が何フレーム目から始まるかを返し（`PcmSource::lastReadTracks()`）、処理経路はそこで区切って段に「曲が始まった」と知らせる（`ProcessingStage::trackStarted()`）。曲が変わったときはその最初のサンプルから新しいゲイン（ギャップレスのまま）。モードを変えたときは 10 ms かけて移る。出力を開く前にも最初の曲を知らせる（それで原音経路か処理経路かが決まる）。原音経路で再生中に、次の曲が処理を要る（ReplayGain がかかる）ときは、つながずに境目で開き直して処理経路にする。
- `ap_play --analyze` にラウドネスと ReplayGain（トラック、複数ならアルバム）を足した。`ap_play FILE... --replaygain track|album` で、再生の前に解析して適用する。画面の文言にも段の名前（ReplayGain）を足した。
- **自動テスト**（完了条件「既知の音源で値が一致」）：
  - 受け入れ：EBU Tech 3341 の統合ラウドネスの試験信号（1 kHz、左右同相、レベルは各チャンネルの dBFS）を生成して測る。ケース1（−23 dBFS → −23.0 LUFS）、ケース2（−33 → −33.0）、ケース3（−36/−23/−36、10/60/10 秒 → −23.0、相対ゲート）、ケース4（−72/−36/−23/−36/−72 → −23.0、絶対ゲート）、ケース5（−26/−20/−26、20/20.1/20 秒 → −23.0）、44.1 kHz でのケース1。どれも ±0.1 LU 以内。
  - 単体：ゲインの式、無音、上限（True Peak が 0 dBTP を超える曲は下げる）、無音は −∞ LUFS、モノラル＝同じ信号のステレオ、アルバムのゲート、段（オフ・値なし・0 dB は何もしない、トラック／アルバム／アルバムがなければトラック、上限、曲が変わると飛ぶ・モードを変えると 10 ms で移る）、Player でギャップレスの2曲のゲインが境目のサンプルで切り替わる（値は float の丸め以内）、原音経路の曲の次にゲインのかかる曲が来ると境目で開き直し、前の曲はビット単位でそのまま。
- **実ファイル**：`ap_signalgen sine --level -23`（48 kHz、20 秒）は −22.99 LUFS（+4.99 dB）。Apple Music Live の 11 曲は −9.4〜−13.1 LUFS（ReplayGain −4.9〜−8.6 dB）、`01 - Immortal.flac` は −6.73 LUFS、`01 - King.flac` は −5.06 LUFS。
- **foobar2000 との比較（2026-11-10、foobar2000 v2.26.2、ReplayGain Scanner の基準 89 dB = −18 LUFS、ユーザーが実施。タグは書き込んでいない）**：Apple Music Live の 11 曲のトラックゲイン（−4.90〜−8.61 dB）、その 11 曲のアルバムゲイン（−7.52 dB）、`01 - Immortal.flac`（−11.27 dB）、iTunes の AAC（+1.97 dB）の **14 項目すべてが表示の桁（0.01 dB）まで一致**。ALAC・FLAC・AAC のデコードからラウドネス、アルバムのゲートまで合っている。foobar2000 のピークはサンプルピークで、こちらのサンプルピークと一致（0.886671 = −1.05 dB、0.892432 = −0.99 dB など）。Immortal は foobar2000 では 0.9856（−0.13 dB）だが、True Peak は +2.96 dBTP：サンプルピークだけを見ると余裕があるように見える例（CLAUDE.md でタグのピーク値を信用しないとした理由）。
- メモ：WAV と ALAC を続けて再生すると、どちらも 16bit でも「形式の切り替え」で開き直す。スピーカー配置の記録（チャンネルマスク）の有無が違うため（前からの動き）。表示が分かりにくいので、経路表示（4-2）で考える。

### 3-5：ISP セーフ、原音モードでの警告、保険のリミッター（2026-11-10）

- **処理の順番**（CLAUDE.md 4章）：ReplayGain → 音量 → （EQ・音作りは 3-6 以降）→ ISP セーフ → 保険のリミッター → TPDF ディザ → 量子化。
- **共通の部品**：音量・ReplayGain・ISP セーフは「10 ms で移る、曲の頭では飛ぶ」ゲインなので、`dsp::GainRamp` にまとめた（音量と ReplayGain の動きは変えていない。既存のテストで確認）。各段は今のゲイン（`peakGain()`）を持ち、処理の列が前の段までの積を後ろの段に知らせる（`setUpstreamGain()`）。
- **ISP セーフ**（`IspSafeStage`）：
  - 計測方式：下げる量 = max(0, 曲の True Peak ＋ 前段のゲイン ＋ 0.5 dB)。ReplayGain や音量で下がった分は差し引く（下げすぎない）。ReplayGain がアルバムのときはアルバムの True Peak（アルバム内の音量の関係を保つ）。解析していない曲は固定の −3 dB。
  - 固定方式：常に −3 dB（ISP 信号では +0.01 dBTP が残り、リミッターが受け持つ）。
  - 曲の頭で切り替わり、前段のゲインが変わったら 10 ms で移る。既定はオフ（原音モード・音作りモードの切り替えと既定値は 3-7 と設定画面 6-3）。
- **保険のリミッター**（`SafetyLimiter`、値は Claude Code が提案し、ユーザーが確認した（2026-11-10）。どれも定数で変えられる）：上限 **−0.3 dBTP**（ISP セーフの −0.5 より上なので普段は働かない）。True Peak の 8 倍の補間で見張り（3-3 のフィルターを共有）、約 1.3 ms（最低 64 サンプル）先を読む：各サンプルの前後 ±先読み/2 に必要なゲインの最小値を移動平均したものなので、ピークが来る前に下がっている。戻りは 50 ms。左右は同じゲイン。働いていないときは、サンプルをそのまま通す（ビット単位で同じ）。それだけでは処理経路にしない（`isIdentity()` は真、`runsWhenProcessing()` が真）ので、原音経路のビットパーフェクトに影響しない。
  - 記録：働いた回数（0.001 dB より多く下げ始めた回数）、下げていたフレーム数、下げた量の最大（`stats()`）。
  - 遅れ：先読みと補間の分（48 kHz で 24 + 64 + 32 = 120 フレーム）。`play()` が補正する：処理した最初の遅れ分を捨て、曲の終わりで遅れ分の 0 を流して中に残った音を出し切る。出力の長さと曲の境目はそのまま（ReplayGain の切り替えも入力の位置で行うので、ずれない）。
- **原音モードでの警告**：Player の状態に今の曲の True Peak（`PlayerStatus::trackTruePeak`、解析の値があるとき）を出す。0 dBTP を超えていて原音経路なら警告を出す（`ap_play` では「ISP の警告」を表示。画面は M4・M6）。その場で ISP セーフをオンにすると、3-2 の仕組みで今の位置で処理経路に開き直す。
- `ap_play --isp-safe off|measured|fixed` を足した（off でも解析して警告する）。処理経路の表示に ISP セーフで下げた量と、終わりにリミッターの記録を出す。
- **自動テスト**（完了条件）：
  - 受け入れ（CLAUDE.md 5章）：ISP 信号（fs/4・45 度・0 dBFS）を 16/24/32bit × 44.1〜384 kHz の WAV に書き、取り込み時と同じくファイル全体の True Peak を測ってから、ReplayGain（オフ）・音量 100%・ISP セーフ（計測）・リミッターを通して 32bit 整数で出す。出力は **−0.5 dBTP 以下**（−0.6 より上：下げすぎない）、フレーム数は入力と同じ、リミッターは働かない（ISP セーフだけで満たす）。
  - 単体：ISP セーフ（オフは何もしない、+2.96 → −3.46 dB、−0.2 → −0.3 dB、−1.0 → 何もしない、前段のゲインの差し引き（音量 −6 dB なら何もしない、ReplayGain +2 dB なら多く下げる）、アルバムの True Peak、解析していない曲は −3 dB、固定 −3 dB、処理の列の中で音量が下げた分を差し引く）。リミッター（上限より小さければビット単位で同じ・長さとタイミングも同じ（周期の長さを変えて）、ISP 信号・隣り合うサンプルがフルスケールで振れる信号・インパルスで出力の True Peak が上限 + 0.05 dB 以内、離れた3回を3回と数える、それだけでは処理経路にしない）、固定 −3 dB の ISP 信号をリミッターが受け持つ、Player が原音経路の曲の True Peak を状態に出す。
- **実ファイル**（`01 - Immortal.flac`、True Peak +2.96 dBTP、ダミー出力）：off は原音経路のまま（ビットパーフェクト）で ISP の警告。measured は ISP セーフ −3.46 dB でリミッターは働かない。音量 −2 dB と一緒なら ISP セーフは −1.46 dB。fixed は −3 dB で、リミッターが 1 回、合わせて 0.28 秒、最大 0.26 dB 下げた。
- **実機確認（2026-11-10、FiiO KA11、排他 WASAPI）**：`01 - Immortal.flac` の 4:20 から 15 秒（4:29 に +2.96 dBTP の箇所）を `--isp-safe measured`（−3.46 dB、リミッターは働かない）と `--isp-safe fixed`（−3 dB、リミッターが 1 回・0.28 秒・最大 0.26 dB）で流し、どちらも違和感なし（ユーザーが確認）。音切れ 0 回。ただしこの曲はデスコアでとても大きく、小さなプチッという音は埋もれて気づきにくい（ユーザーの指摘）ので、プチッという音の確認は 3-6・3-7 で静かな曲を使った。効果（聞こえ方がよくなる）は謳わない。

### 3-6：パラメトリック EQ（2026-11-10）

- **フィルター**：最小位相の IIR。Audio EQ Cookbook（Robert Bristow-Johnson）の双二次フィルターを 64bit で（直接形 I）。ピーキング・ローシェルフ・ハイシェルフ・ローパス・ハイパス、最大 32 バンド。周波数が 0.49 fs 以上のバンドは作れないので飛ばし、数を記録する（例：44.1 kHz で 22 kHz のバンド）。
- **直線位相はフェーズ2**（Claude Code が提案し、ユーザーが確認した（2026-11-10））：長い FIR の畳み込み（区切って FFT で計算する）が要り、フェーズ2 の IR 畳み込み（quality-measures の 14）と同じ部品なので、そこで一緒に作る。
- **プリアンプ自動**：つないだ全体の特性を 20 Hz〜0.49 fs で細かく（対数で 2000 点と各バンドの中心）計算し、最大のブーストだけ前もって下げる（EQ が 0 dB より上に持ち上げる周波数はなくなる）。削るだけの EQ ではプリアンプは 0 dB。AutoEQ のファイルに書かれた Preamp は表示だけ。EQ の段の「ピークの倍率」は 1 として扱う（位相の回り方でピークが上がることがあるので、ISP セーフの計算で EQ の分を差し引かない）。
- **値の切り替え**：再生中に値を変えると、古いフィルターと新しいフィルターの出力を 10 ms で混ぜて移る（係数が急に変わるプチッという音を防ぐ）。再生のスレッドは待たない（ロックを取れたときに新しい値を受け取る）。全部 0 dB に戻したときは、混ぜ終わるまで「何もしない」状態にしない（フィルターが急に外れないように）。
- **何もしない状態**：有効なバンドがすべて 0 dB のピーキングかシェルフ（ローパス・ハイパスなし）なら、何もしない（バイパスが成り立つ）。
- **AutoEQ の読み込み**：`ParametricEQ.txt` と Equalizer APO の書き方（`Preamp: -6.2 dB`、`Filter 1: ON PK Fc 105 Hz Gain -3.1 dB Q 0.70`、`Filter:` だけの行も）。種類は PK/PEQ、LS/LSC、HS/HSC、LP/LPQ、HP/HPQ。OFF のフィルターは飛ばし、読めない行（対応していない種類、数字でない値、`Channel:` などほかの命令）は警告を出して飛ばす。UTF-8 の BOM と CRLF に対応。
- `ap_play --eq PRESET.txt` を足した（バンドの数、警告、自動のプリアンプ、飛ばしたバンドを表示）。処理の順番は ReplayGain → EQ → 音量 → ISP セーフ → 保険のリミッター。画面の文言に段の名前（パラメトリック EQ）を足した。
- **自動テスト**（完了条件「周波数特性の測定テスト」）：
  - 測定：4 バンド（ローシェルフ +4.5 dB、ピーキング −3.2 dB と +5 dB、ハイシェルフ −4 dB）の EQ に 40 Hz〜18 kHz の 8 つの周波数のサイン波を通して出力の大きさを測り、設計の特性＋プリアンプと **0.01 dB 以内**で一致。
  - 設計：ピーキングは中心でちょうどそのゲイン、シェルフは端でそのゲイン、ローパス（Q 0.707）は遮断周波数で −3.01 dB。5 種類とも、別に書いたアナログの原型の式（双一次変換の周波数のゆがみ込み）と 1e-6 dB 以内。
  - プリアンプ：最大のブーストが 0 dB になる、削るだけなら 0 dB。何もしない状態（0 dB、オフのバンド、パス系は何もしなくない）。値の大きな切り替え（+0.5 → +12 dB）でも波形に段差がない。0 dB に戻すと混ぜ終わるまで何もしない状態にならない。AutoEQ・Equalizer APO の読み込みと警告。レートで作れないバンドを数える。
  - 受け入れ（EQ 全 0 dB・音作りオフ：バイパスが成立し、原音モードと出力が一致）：3-1 の 72 通りの処理の列に、4 バンドすべて 0 dB の本物の EQ を入れても原音経路とビット単位で一致。
- **実機確認（2026-11-10、FiiO KA11）**：手持ちのヘッドホンの AutoEQ のファイルはなかったので、テスト用の設定（ローシェルフ 105 Hz +5.5 dB、ピーキング 2.9 kHz +3 dB、ハイシェルフ 10 kHz −4 dB、ピーキング 21.5 kHz +2 dB。自動のプリアンプ −5.49 dB）で、静かな曲 `01 - Your Song (Apple Music Live).m4a` の 0:30 から 20 秒を流した。プチッという音も歪みもなし（ユーザーが確認）。リミッターは働かず、音切れ 0 回。効果は謳わない（AutoEQ の補正が好みかどうかは人による）。

### 3-7：原音と音作りの聴き比べ（2026-11-10）

- **作り方（ユーザーと決めた：案 A）**：原音経路と処理経路では送る形式が違うので、普段の切り替え（原音モード ⇄ 音作りモード）は出力を開き直す（原音は本当のビットパーフェクト）。聴き比べ（A/B、のちの ABX）のときだけ、処理経路の形式で出力を開き、同じ入力から原音と音作りの両方を作って、5 ms のクロスフェード（レイズドコサイン）で切り替える。聴き比べに入る・出るときは開き直す（遅れの量が変わるため）。
- **聴き比べ中の原音側**：値はそのまま（浮動小数点で出せば入力とビット単位で同じ、整数ならディザの ±1 LSB だけ）。処理経路を通るのでビットパーフェクトではない、と表示する。音作り側の遅れ（リミッターの先読み）と同じだけ遅らせて、時間をそろえる（ずれたまま混ぜるとくし形フィルターになる）。
- **音量合わせ（ユーザーと決めた：音作り側を原音に合わせる）**：両方の信号に BS.1770 の K 特性をかけ、聴き比べを始めてからのエネルギーを積み上げ、その比を音作り側のゲインにする（10 ms ごとに更新、10 ms で移る、±24 dB まで）。ゲインだけの差（音量、ReplayGain、ISP セーフ、EQ のプリアンプ）はすぐに正確に合う。そのあとに聴き比べ用のリミッター（−0.3 dBTP）を通す。
- **合わせきれない場合**：原音のピークがリミッターの上限より高い曲（大きく作られたマスター）では、合わせた音作り側が上限を超え、リミッターが下げるので、同じ音量にはできない（クリップさせない限り）。合わせるゲインを追いかけて上げることはしない（際限なく上がる）。代わりに、出てくる音どうしの音量差（`levelDifferenceDb()`）を測って表示する。例：`01 - Immortal.flac`（True Peak +2.96 dBTP）に EQ と ISP セーフをかけて聴き比べると、合わせるゲイン +7.30 dB、聴き比べ用のリミッターが 74 回（最大 4.33 dB）働き、音量差 −0.91 dB。
- **残っている課題（4-1 ABX で）**：EQ をかけると、ラウドネスの変わり方は音の周波数成分によるので、曲が進むと合わせるゲインが動く。聴き始めの数秒はそろいきらない（11 秒の書き出しで、リミッターが働かないのに −0.12 dB）。音作り側の曲全体のラウドネスを先に解析して、曲ごとに決まったゲインで合わせる方法を、ABX と一緒に入れる。
- `ap_play --compare original|processed` と `--compare-at S` を足した。経路の記録に `comparison`、段の名前に「聴き比べ」。
- **自動テスト**（完了条件「切り替え前後の音量差テスト」）：
  - 受け入れ：成分の変わらない多音の信号（60 Hz〜14 kHz の 40 音）に、EQ（+6 dB のピーク、−4 dB のハイシェルフ、自動プリアンプ）と音量 −6 dB をかけて聴き比べ、原音 → 音作り → 原音と切り替える。各区間のラウドネスを libebur128 で測り（聴き比べの K 特性とは別の実装）、**差が 0.1 dB 以内**（44.1・48・96 kHz。実測 0.0018 dB）。聴き比べが報告する音量差も 0.1 dB 以内。原音の区間は入力とビット単位で同じ。音作りの区間は入力と違う（EQ がかかっている）。
  - 単体：クロスフェードが 5 ms（48 kHz で 240 フレーム、単調）、ゲインだけの差はすぐに合う（−6 dB → +6.00 dB）、原音側の遅れが音作り側とそろう、大きく作られた原音では合わせきれず音量差を報告する、聴き比べに入ると処理経路（32bit）、出ると原音経路に戻る。
- **実機確認（2026-11-10、FiiO KA11）**：同じ曲・同じ部分・同じテスト用の EQ で `--compare original --compare-at 5 --compare-at 10 --compare-at 15`（原音 → 音作り → 原音 → 音作り）。切り替えのところでプチッという音はなく、音量もそろって聞こえた（ユーザーが確認）。音作り側の合わせるゲインは +5.14 → +5.12 → +5.06 → +5.08 dB とほとんど動かず、出てくる音の音量差は +0.03 dB。どちらのリミッターも働かず、音切れ 0 回。

### 4-1：ABX（2026-11-10）

- **決めたこと（ユーザーと）**：正解数と p 値は最後まで隠す（途中で見ると、当たっているところでやめる偏りが入り、p の意味が崩れる）。中断したら結果は出さない。「区別できた」と書く基準は p < 0.05。p の値そのものも必ず出す。
- **判定**（`AbxTest`、画面に依存しない）：既定 16 回。回ごとに X が A（原音）か B（音作り）かを OS の暗号用の乱数（BCryptGenRandom）で決める。A・B・X は何度でも切り替えて聴ける（3-7 の聴き比べ、5 ms のクロスフェード）。答えは「X は A」か「X は B」。p は当てずっぽうでこれ以上当たる確率（二項分布の片側、正確な値）。文言は「偶然とは考えにくい（聞き分けられた可能性が高い）」か「偶然でも十分に起こりうる（聞き分けられたとは言えない。違いがないという意味ではない）」まで。どちらの音がよいかは言わない。
- **音量差の確認**：テスト中の音量差（聴き比べが測る、出てくる音どうしの差）の最大を結果に残し、0.1 dB を超えたら「結果は参考（音量の違いで聞き分けた可能性）」と出す。
- **3-7 の持ち越しを解決**：曲全体の音量合わせ（`measureMatchDb`）。同じ設定で作った別の処理の列に曲全体を通し、原音と音作りの K 特性のエネルギーの比から、その曲で決まったゲインを出す（`AbComparison::setFixedMatchDb`）。EQ や、のちの真空管などの段もそのまま計算に入る。前半と後半で音色が違う信号に高域のシェルフ EQ をかけても、曲全体のラウドネスの差は 0.1 dB 以内（libebur128 で確認）。

### 4-2：経路表示と BIT-PERFECT の判定（2026-11-10）

- **判定**（`judgeBitPerfect`、エンジン）：経路の記録（事実）から判定する（CLAUDE.md 8章）。BIT-PERFECT は「アプリからドライバーまで、サンプルの値がそのまま届く」こと。原音経路なら成り立つ。処理経路では成り立たず、理由を段ごとに今の値で出す（「DIGITAL VOL -6.0 dB」「ReplayGain -5.6 dB」「パラメトリック EQ（プリアンプ -5.5 dB）」「ISP セーフ -3.0 dB」「浮動小数点の曲を整数に変換」「聴き比べ中」「TPDF ディザ」）。保険のリミッターは理由にしない（処理経路では常に通るが、それだけでは値を変えない）。
- **扱いを決めたこと（Claude Code が提案し、ユーザーが確認した（2026-11-10））**：(1) コンテナの詰め替え（24bit → 32bit コンテナ、16bit → 24bit）は、値が同じなので BIT-PERFECT のまま「詰め替えあり、値は同じ」と注記する。CLAUDE.md 8章の「出力形式が一致」を厳密に読むと外れるが、利用者に大事なのは値が変わったかどうか、と考えた。(2) デバイス側の音量（Windows の音量がデバイスの中でかかる場合）は、DAC に届いたあとの話なので判定は変えず、「この判定はドライバーまで」と注記する。(3) DoP は「DSD を DoP でそのまま」、非可逆の曲は「デコードした値のまま」と注記する。
- **段ごとの今の状態**：処理の段に、今かけている量（`displayGainDb()`：音量、ReplayGain、ISP セーフ、EQ のプリアンプ）を足し、処理の列から取り出せるようにした（`activeStageStates()`）。Player の状態に `stages`（処理経路のとき）と `bitPerfect`（判定）を載せる。

### 4-3：ビットパーフェクトの自己確認（2026-11-10）

- **何をするか**（`DeliveryCheck`、エンジン）：原音経路で、周期ごとに「ファイルから読み出した値」と「出力層がドライバーのバッファーに実際に書いた値」を比べ、一致したフレーム数と一致しなかったフレーム数を数える。比べる場所は、WASAPI は `GetBuffer` で受け取ったデバイスのバッファー（`ReleaseBuffer` の直前）、ASIO はドライバーのチャンネルごとのバッファー（並べ替えたあと）、ダミー出力は書き出すデータ。
- **値の比べ方**：両方を同じ形（整数は 32bit に左詰め、浮動小数点はビット列のまま）に直して比べる。コンテナの詰め替え（24bit → 32bit コンテナ）や ASIO の右詰めの型（Int32LSB24 など）は、値が同じなら一致になる（4-2 の扱いと同じ）。
- **どこまで確かめられるか**（画面にも書く）：アプリからドライバーまで。ファイル → デコードは MD5 の照合（「ファイルの検証」）が受け持ち、自己確認はデコード → ドライバーのバッファーを受け持つ。ドライバーの中、USB などの転送、DAC の中はアプリからは見えない。確かめるには DAC 側の機能（ビットパーフェクトの表示など）か、デジタル出力を別の機器で録って比べる方法が要る。
- **確かめる中身の濃さは経路によって違う**：ASIO（並べ替えと型の変換がある）と詰め替えありの経路では、アプリの中の変換を確かめている。WASAPI で詰め替えなしの場合は、デコーダーがデバイスのバッファーに直接書くので、比べるのは同じ場所の値になる（読み出した直後と、ドライバーに返す直前）。その間に何も書き換えていないことの確認にとどまる。
- **判定とのつながり**：一致しないフレームが 1 つでもあれば BIT-PERFECT を外し、理由に「自己確認で不一致（N フレーム）」と出す。処理経路では行わない（値を変える経路なので）。数えるのは出力を開いてから（形式が変わって開き直すと 0 から）。
- **表示文言（ユーザーが確認した（2026-11-10））**：最初の案は不一致の文が分かりにくかった（数える期間がかっこの最後にあり、「フレーム」の説明がなく、性質の違う 2 つが同じかっこに入っていた）。期間を文の頭に出し、一致の文と同じ組み立てにして、フレームの説明を足した。
  - 一致：「この出力を開いてから 2 分 5 秒分、ドライバーに渡した値はすべて、ファイルから読み出した値と一致しました。確かめられるのはアプリからドライバーまでです。ドライバーの中、USB などの転送、DAC の中は確かめられません」
  - 不一致：「この出力を開いてから、ドライバーに渡した値のうち 3 フレーム分（1 フレーム＝全チャンネル 1 組の値）が、ファイルから読み出した値と違っていました。アプリの不具合と考えられます」（比べているのはアプリの中なので。ファイルの傷は MD5 の照合が、DAC はこの比較に関わらない）
  - 始まったばかり：「確認中（最初のデータを渡すと結果が出ます）」
  - 処理経路：「処理経路では行いません（値を変える経路のため。原音経路で、渡した値と読み出した値を比べます）」
- 画面の経路の欄に「自己確認」の行を足した。橋渡しに `delivery`（一致・不一致のフレーム数）と `bitPerfect.deliveryMismatch` を足した。模擬エンジンも数を返す。`ap_play` は終わったときに「自己確認（最後に出力を開いてから）」の行を出す。
- **自動テスト**：同じ値で一致、1 ビット違うと 1 フレームの不一致、詰め替え（24 → 32bit コンテナ）は一致・16bit に削ると不一致、ASIO の Int24LSB・Int32LSB・Int32LSB24 で一致し、ドライバーのバッファーの 1 ビットの違いを見つける、渡していない・読んでいない・チャンネル数が違うフレームは不一致、Player を通して：ダミー出力（詰め替えなし・あり、周期をずらす）と偽の ASIO ドライバー（Int24LSB、Int32LSB）で全フレーム一致、処理経路では行わない、不一致で BIT-PERFECT が外れる。画面の文言：各場面の文と、不一致のときの BIT-PERFECT の理由。模擬エンジンでブラウザーに表示されることも確かめた。

### 4-4：True Peak と LUFS のメーター（2026-11-11）

- **何を測るか**（Claude Code が決めた。U に確認してもらう）：出力層に渡す値。処理経路では処理の後（ISP セーフやリミッターの効果がそのまま見える）、原音経路では原音そのもの。「出力の確認」画面のメーターなので、DAC に向かう信号を測る。DoP は PCM の音の値ではないので測らない（理由を表示する）。測るだけで、音は変えない。
- **値**（`LevelMeter`、エンジン）：
  - True Peak：3-3 と同じ 8 倍の補間で、チャンネルごとに「直近（0.1〜0.2 秒）」と「この曲の最大」。
  - ラウドネス（libebur128、BS.1770）：瞬時（400 ms）と短時間（3 s）は曲の境目をまたいで続く窓（いま聞こえているもの）。統合値は曲の頭から（ゲートあり）。モノラルはデュアルモノ（3-4 と同じ）。
  - 曲の頭で最大と統合値を 0 に戻す。補間はサンプルより半窓（24 サンプル）遅れて値が出るので、境目より前の時刻の値は新しい曲に数えない。ギャップレスの境目でも、周期の途中の正確なフレームで切り替える。
  - 同じ曲を途中から続けるとき（停止 → 再開、処理経路の切り替えで開き直した）は値を続ける。曲を頭から再生し直したときは 0 から。シークでは続ける（「この曲で流した部分」の値）。
- **音を邪魔しない作り**（`OutputMeter`）：再生スレッド（ASIO ではドライバーのスレッド）は、渡したバイト列を前もって確保したリング（約 1 秒分、1024 フレームずつの区画）にコピーするだけ。補間と K 特性の計算はメーター専用のスレッドで行う（10 ms ごとに取り出し、50 ms ごとに値を出す）。メーターが追いつかずリングがあふれたら、その分は測らずに数える（「計算が追いつかず ○ フレームを測れなかった（音には影響しない）」）。待たない。ダミー出力はデバイスの速さで進まない（実時間より速い）ので、テストと `ap_play --dummy` ではメーターが待つ設定にする。
  - 速さの目安（Release、60 秒のサイン波、ダミー出力。ファイルの読み書きとハッシュ込みの時間）：44.1 kHz で 1.2 秒、192 kHz で 2.9 秒、384 kHz（2ch）で 5.1 秒。メーターは実時間の約 12 倍以上の速さで測れている。
- **表示**：画面に「メーター」の欄（文字。バーは 6-4）：True Peak（今）、この曲の最大（0 dBTP を超えたら「0 dBTP を超えています」）、ラウドネス（瞬時 ／ 短時間）、この曲の統合値（この曲の何秒分か）、何を測っているかの注記。停止中は曲の値だけ残す。曲が変わった直前後は、前の曲の値を新しい曲の値として出さない。`ap_play` は再生中の行に「TP … dBTP  M … / S … LUFS」、終わりに曲の値。
- **自動テスト**（完了条件「テスト信号で値が合う」）：
  - 受け入れ（Tech 3341 と同じ作りの信号。1 kHz、左右同相、各チャンネルの dBFS がそのまま LUFS）：窓と同じ周期で切り替わる信号で、瞬時（−20 dBFS 0.18 s ／ −30 dBFS 0.22 s）と短時間（1.34 s ／ 1.66 s）が窓が埋まってから常に **−23.0 ± 0.1 LUFS**。−23 dBFS の一定の音が瞬時・短時間・統合とも −23.0（44.1・48・96 kHz）。ゲートの効く信号（3-4 のケース 4 の並び）で統合値が −23.0 で、解析（`LoudnessMeter`）と同じ値。曲の頭で統合値が 0 から（−23 の曲の次の −33 の曲が −33.0）、窓は続く。モノラル。ISP 信号（fs/4・45 度・0 dBFS、フェードあり）が **+3.01 ± 0.02 dBTP** で、ファイル全体の解析（3-3）と同じ値（44.1〜384 kHz）。チャンネルごとの値（−6 / −12 dBFS）。
  - 単体：初めは無音、直近の値は下がり最大は残る、0.09 秒前のピークは直近に入る、小分けにしても同じ値、曲の頭で最大が 0 から、境目より前の補間の値を新しい曲に数えない、`finish()` で最後のサンプルの後ろまで測る。
  - メーター（リングとスレッド）：周期の途中で曲が始まっても、その曲の統合値が「その曲だけを解析した値」とビット単位で同じ。追いつかなかった分は数えられ、測った分＋数えた分＝渡した分（384 kHz・8ch を一度に 30 秒分）。DoP は測らない。途中から続けるか頭からかの扱い。

### 5-1：ライブラリの DB 設計（2026-11-11）

- **依存**：SQLite 3.50.4（amalgamation、パブリックドメイン。SHA-256 固定）。`sqlite3.c` を FTS5 つき（5-4 の trigram 用）で静的ライブラリにする。実行時の拡張の読み込みは切った。THIRD_PARTY_NOTICES に追記した。
- **置き場所**：新しく `library/`（静的ライブラリ `ap_library`。UI にもエンジンにも依存しない）。CLAUDE.md 9章の構成に足した。
- **表の分け方**（スキーマ v1、`library/src/library_schema.cpp`）：
  - `roots`（監視フォルダー）、`files`（場所。パス、NTFS のボリュームシリアル＋128bit のファイル ID、サイズ、更新日時、タグ領域のハッシュ、見つからない印）。
  - `tracks`（音の一まとまり）：ファイルとは別の表にした。編集・評価・再生履歴・測定値はこちらにぶら下がるので、改名や移動で場所が変わっても残る（5-5）。別のドライブや NAS で見つけ直すための音声データの指紋（FLAC は STREAMINFO の MD5）の列も持つ。将来の CUE シート（1 ファイルに複数の曲）のために、曲の範囲の列を用意した（今は NULL＝ファイル全体）。
  - `track_fields`（表示値の 3 層）：1 行が「曲・項目・層・何番目・値」。層は 0 タグ、1 外部DB、2 ユーザーの修正。**項目ごとに、値を持ついちばん上の層を表示する**（ビュー `track_values`）。ユーザーが項目を「空にする」修正も記録できる（値なしの行。ユーザーの層だけに許す）。複数の値（共演のアーティストなど）は順番つきで持つ。項目名は Vorbis コメントにならった小文字（title、artist、albumartist、composer、work、movementname など。クラシックの項目もそのまま入る）。値の出どころ（`id3v2.3`、`musicbrainz` など）も残す。
  - `track_analysis`（True Peak・サンプルピーク・その位置・統合ラウドネス。測り直しの判断のために、解析の版と、測った音の指紋を持つ）と `album_analysis`（アルバムをまとめてゲートをかけたラウドネスと最大の True Peak。どの曲で測ったかのハッシュを持つ）。タグのピーク値は使わない。
  - `provenance_findings`（ファイルの素性鑑定、フェーズ2）：調べた項目（CD との一致、アップサンプリング、非可逆からの変換、ビット深度の水増し、プリエンファシス、極性、左右の時間差）ごとに、結果（`found`／`none`／`inconclusive`）と根拠の測定値（JSON）。**直す列は作っていない**（提案のみで自動では直さない、という方針を表の形でも守る）。
  - `plays`（再生履歴：始めた時刻、流したフレーム数、最後まで聴いたか）と `tracks.rating`（0〜100、NULL は未評価。星の数などの見せ方は画面で決める）。
- **マイグレーション**（`migrate()`）：版は SQLite の `user_version`。1 段ずつ 1 つのトランザクションで行い、途中で失敗したらその段は丸ごと戻る（前の段までは残る）。既にある DB を変える前に `<DB>.v<元の版>.bak` へ丸ごと写す（SQLite のオンラインバックアップ）。**新しいアプリが作った DB（版が上）は一切触らずにエラーにする**（古いアプリで開いて壊さないため）。一度出したマイグレーションは書き換えず、新しい段を足す。検索（FTS5 trigram）は 5-4 で 2 段目として足す。
- 開いたあと WAL モードにする（画面の読み取りがスキャンの書き込みを待たない。落ちても書きかけの DB にならない）。外部キーは常に有効。
- **自動テスト**（完了条件「スキーマとマイグレーション」、16 件）：
  - マイグレーション：新しい DB は全段、最新の DB はそのまま（バックアップも作らない）、既にある DB はデータが残り、変える前の DB がバックアップに残る（版 1、新しい列なし、データあり）、失敗した段は丸ごと戻る（同じ段の最初の文で作った表も残らない）、新しいアプリの DB はファイルのバイト列が変わらない、段の番号の抜けを断る、ライブラリの DB が最新の版で作られ、表がそろい、外部キーが有効で整合している。
  - 3 層：タグだけならタグ、外部DB はタグより上、ユーザーの修正がいちばん上、項目ごとに別の層、ユーザーの修正を取り消すと下の層が出る、ユーザーが空にした項目は空、複数の値の順番、層の値の置き換え。
  - 表：大文字小文字だけ違うパスは同じファイル、同じボリュームの同じ NTFS ID は同じファイル（別のボリュームなら別）、ファイルが見つからなくなっても曲・評価・履歴は残り、別のドライブで見つけたファイルにつなぎ直せる、ファイルを外すと曲にぶら下がるもの（表示値・履歴・解析・鑑定）も消える、評価の範囲・「空にする」はユーザーの層だけ・鑑定の結果は 3 種類で根拠は JSON・存在しないファイルの曲は作れない。
- 5-2 以降への申し送り：DB の置き場所（`%LOCALAPPDATA%` の下。MSIX ではパッケージごとに振り替えられる）はアプリに組み込むときに決める。古い ID3 の文字コードの判別結果（5-3）、検索用の表（5-4）は、それぞれの段で足す。最後に使ったビュー（6-7）などの設定は、ライブラリの DB ではなく設定ファイルに持つ予定。

### 5-2：監視フォルダーと起動時の差分スキャン（2026-11-11）

- **比べ方**（`Scanner`）：監視フォルダーの中の音楽ファイル（エンジンが開ける拡張子：wav、flac、aif、aiff、aifc、m4a、mp3、dsf、dff。大文字小文字は問わない）を、ディレクトリの一覧（ファイルを開かない）でサイズと更新日時ごとに集め、DB と比べて分ける。
  - 追加：DB にない。曲を作り、タグを読む印（`needs_read`）を付ける。
  - 変更：サイズか更新日時が違う。読み直す印を付ける（同じ曲のまま）。
  - 見つからない：DB にあってディスクにない。行は消さず、見つからない印だけ付ける（評価・履歴・修正は残る）。同じものを 2 度は報告しない。
  - 戻った：見つからない印の付いたファイルが、同じ場所にまたある。
  - 移動・改名：DB が場所で知らないファイルだけ、属性だけを読む権限で開いて NTFS の ID（ボリュームシリアル＋128bit のファイル ID）を読む。知っている ID なら同じ曲の場所を直す。フォルダーの改名でも中の曲はそのまま。ハードリンク（同じ ID の別名）は、元の名前が残っていれば別のファイルとして ID なしで加える。別のドライブへの移動（ID が変わる）は 5-5 で音声データの指紋で追う。
  - フォルダー全体（起動時）と、1 つの場所（ファイル、フォルダー、もう無いもの）の 2 通り。1 回の比較は 1 つのトランザクション（そのため、トランザクションを入れ子にできるようにした。中のものは SAVEPOINT）。
- **DB の 2 段目のマイグレーション**：`files.needs_read`（タグを読む印。5-3 が読んで外す）。5-1 の仕組みで足した最初の段。
- **起動中の監視**（`FolderWatcher`、`LibraryMonitor`）：
  - 監視フォルダーごとに ReadDirectoryChangesW（重なった I/O、サブフォルダーも、ファイル名・フォルダー名・サイズ・書き込み時刻の変化）を専用のスレッドで待つ。フォルダーの削除や改名を妨げない開き方。
  - **先に監視を始めてから起動時のスキャンをする**（スキャン中の変化を取りこぼさない）。
  - 変化が 0.3 秒落ち着いてから、変わった場所だけを比べ直す（アルバムのコピーは大量の通知になるため）。ある場所の中の場所は、外側の 1 回にまとめる。
  - **バッファーがあふれたら**（Windows がどれが変わったかを言えない）、そのフォルダー全体を比べ直す。監視が止まったとき（フォルダーが消えた、ドライブが外れた）も全体を比べ直し、中の曲は「見つからない」になる。
  - バッファーは 64 KB（ネットワーク越しで使える上限）。1 回の比較の失敗は記録して続ける。
  - 自分の DB 接続を持つスレッドで動く。画面は別の接続で読む（WAL なので待たない）。
- **自動テスト**（完了条件「追加・変更・削除・バッファーあふれのテスト」、13 件）：
  - スキャン：音楽ファイルだけを加える（日本語の名前、大文字の拡張子、jpg・txt は無視）、変わっていなければ何もしない、サイズの変化と同じサイズで新しい時刻の両方を「変更」、削除は「見つからない」で評価が残り、戻せば同じ曲、改名とフォルダーの改名で同じ曲、1 つの場所（追加、フォルダーが消えたら中が見つからない、名前の始まりが同じ別のフォルダーは含めない）、根の外の場所は断る、NTFS の ID が読める。
  - 監視（一時フォルダーで実際の ReadDirectoryChangesW）：変化の通知、起動時のスキャン、アルバムのフォルダーを加える・ファイルを書き換える・フォルダーの改名（曲の数は変わらない）・削除、**あふれ**（バッファーを 512 バイトにし、読むたびに 0.3 秒休ませて 300 ファイルを作る：あふれを起こし、全体を比べ直して 300 曲そろう）、監視フォルダーを丸ごと消すと中の曲は「見つからない」で残る。5 回続けて走らせて安定（約 3 秒）。
- **アプリへの組み込み**（監視フォルダーの追加の画面、DB の置き場所、起動時に `LibraryMonitor` を動かす）は 6-1 で行う。

### 5-3：タグの読み取りと Shift_JIS の自動判別（2026-11-11）

- **依存**：TagLib 2.1.1（LGPL-2.1 か MPL-1.1。LGPL で静的に組み込む。ソースを公開しているので利用者が差し替えてリンクし直せる）。同梱の utfcpp は BSL-1.0。再生しない形式（ASF、トラッカー形式、Shorten、TrueAudio）と zlib（圧縮された ID3v2 フレーム、まれ）は外した。THIRD_PARTY_NOTICES に追記した。**タグは読むだけで、書き込みには使わない。**
- **判別が要るところ**：文字コードを宣言しない欄だけ。ID3v1、ID3v2 で「ISO-8859-1」と印の付いたフレーム、WAV の RIFF INFO。規格上は ISO-8859-1（INFO は TagLib では UTF-8 扱い）だが、実際には書いたソフトの PC のコードページ（日本語の Windows なら Shift_JIS）で入っている。UTF-16 の ID3v2、FLAC の Vorbis コメント、MP4（iTunes）など宣言のある欄はそのまま（手持ちの iTunes の AAC の日本語の曲名も正しく出た）。
- **作り**：TagLib の文字列の扱いを差し替え、宣言のない欄はバイト列のまま受け取る（ASCII 以外は私用領域の文字に一時的に置く）。読み終えてから、**ファイルの中の欄をまとめて 1 つの文字コードに決める**（1 つのファイルは 1 つのソフトが書くため）：
  - UTF-8：宣言のない欄がすべて正しい UTF-8（ISO-8859-1 の欄に UTF-8 を書くソフトがある）。
  - Shift_JIS（CP932：Windows の NEC・IBM 拡張込み）：かな、和文の記号、全角英数、丸数字、半角カナ 3 文字以上の並び、のどれかがある。または第 1 水準の漢字が合わせて 2 字以上。
  - それ以外は Windows-1252（ISO-8859-1 に、曲がった引用符・ユーロ記号などを足したもの）。
  - 西洋の文字が偶然 Shift_JIS としても読める場合があるので、それだけでは日本語と判断しない。例：「Hélène」は第 2 水準の珍しい漢字になり、「Don’t」の曲がったアポストロフィーは第 1 水準の漢字 1 字になる。ö・ó・ñ などは外字の領域になる（そこで Shift_JIS ではないと分かる）。
  - そのファイルの文字コードで読めない欄は、その欄だけ Windows-1252 で読む。
  - 「〜」は Windows の Shift_JIS では U+FF5E（～）になる（いわゆる波ダッシュの問題）。Windows のとおりにした。
- **DB**（3 段目のマイグレーション）：ファイルごとに判断した文字コード（`tag_charset`）、利用者の指定（`tag_charset_override`。判断の代わりに使う）、読めなかった理由（`read_error`）。タグは表示値の「タグ」の層に入れ直す（利用者の修正と外部 DB の層はそのまま。修正した値は新しいタグより上に出る）。読めなかったファイルは、次にファイルが変わるまで読み直さない。
- **監視とのつながり**：`LibraryMonitor` が比べるたびに、印の付いたファイル（`needs_read`）のタグを読む。
- **ap_lib**（新しい道具）：`ap_lib scan FOLDER --db FILE` で実際のフォルダーを DB と比べてタグを読み、`ap_lib show --db FILE [--charset shift_jis]` で曲の一覧（表示値と文字コードの判断）を出す。音楽ファイルは読むだけ。
- **自動テスト**（完了条件「文字化けサンプルで正しく判別」）：
  - 判別（8 件）：Shift_JIS（かな、漢字だけの「千本桜」、記号、丸数字・全角、半角カナ）が日本語に。西洋の文字（Café、Björk、Sigur Rós、Mötley Crüe、Hélène、Don’t Stop Me Now、Ça va、Señor、Für Elise、Åsa、€・ダッシュ・曲がった引用符）が Shift_JIS と間違われずに正しく読める。ISO-8859-1 の欄の UTF-8。ASCII だけなら判断しない。ファイルの中の欄をまとめて判断（半角カナ 1 字だけ・漢字 1 字だけでは判断せず、同じファイルのほかの欄で決まる）。読めない欄はその欄だけ別に読む。
  - **文字化けサンプル**（ファイルをバイト単位で作って TagLib で読む）：ID3v2.3 の「ISO-8859-1」のフレームに Shift_JIS（夜明けのスキャット／由紀さおり／ベスト）、ID3v1 だけの MP3（千本桜／黒うさＰ／ﾃｽﾄ）、WAV の RIFF INFO（録音テスト／山田）が正しい日本語になる。同じ作りの西洋の文字は Windows-1252 のまま。UTF-16 の ID3v2 と FLAC の Vorbis コメント（同じ項目の複数の値は順番どおり）はそのまま。利用者が文字コードを指定すればそれで読む（Shift_JIS の「テスト」を Windows-1252 と指定すると「ƒeƒXƒg」）。TagLib が読めないファイルはエラー。
  - DB への取り込み：スキャンで印の付いたファイルを読み、Shift_JIS の判断・読めない理由を記録、2 回目は読むものがない、利用者の修正は読み直しても残る、文字コードの指定と取り消しで読み直す。
  - 全体 398 件が通った。ライブラリのテストは AddressSanitizer（TagLib を含む）でも確認。
- **手持ちのファイルでの確認**：`テスト用音源` の 28 ファイル（FLAC・WAV・AIFF・ALAC・AAC・MP3）を `ap_lib scan` で比べてタグを読んだ：比較 0.00 秒、タグ 0.12 秒、読めなかった 0。iTunes の AAC の日本語の曲名も正しく出た。この中に宣言のない日本語のタグを持つファイルはなかった。
- **手持ちの古い MP3 での確認**（2026-11-11）：ユーザーの手元に、宣言のない日本語のタグを持つ古い MP3 がなかった。完了条件は作ったサンプルで満たしているので完了とし、見つかったときに試す（任意）。手順：古い MP3（2000 年代に日本語の Windows のソフトでタグを付けたものなど）があれば、そのフォルダーで次を実行し、文字化けせずに出るかを確かめる。DB は試し用で、どこに作ってもよい（音楽ファイルは読むだけ）。
  1. `build\vs2022\tools\library\Release\ap_lib.exe scan "古い MP3 のフォルダー" --db "$env:TEMP\ap_lib_check.db"`
  2. `build\vs2022\tools\library\Release\ap_lib.exe show --db "$env:TEMP\ap_lib_check.db" --charset shift_jis`（Shift_JIS と判断した曲だけ）。`--charset` を付けなければ全部。
  3. 文字化けしている曲があれば、そのファイル名と、正しい曲名を教えてもらう（判別の規則を見直す材料にする）。
