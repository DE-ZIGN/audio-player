## 記録

### S1：排他モードで受け付ける形式（`ap_play --formats`、2026-11-08）

| デバイス | Windows の既定の形式 | 排他モードで受け付けた形式 |
|---|---|---|
| SSL 2 MKII USB Audio Device | 96 kHz / 32bit | 96 kHz のみ（16bit、24bit を 32bit コンテナに入れた形、32bit）。24bit パックは不可 |
| NVIDIA High Definition Audio（PL2473H） | 48 kHz / 16bit | 44.1 / 48 kHz の 16bit のみ |
| Waves SoundGrid | 44.1 kHz / 32bit 浮動小数点 | 44.1 kHz の 32bit 整数のみ |

### S1-実機：再生の結果（2026-11-08）

| 項目 | 結果 |
|---|---|
| 96 kHz / 24bit（32bit コンテナに詰め替え）、1 kHz −40 dBFS、10秒を SSL 2 MKII で再生 | 聞こえた、途切れなし（ユーザー確認）。送ったフレーム 960000 / 960000、周期 10 ms（960 フレーム）、デバイス待ちのタイムアウト 0 回 |
| ほかのアプリの音が混ざらないか | 混ざらない（ユーザー確認）。再生中は YouTube（ブラウザー）が再生を始められず、読み込み中の表示のままだった＝ブラウザーがデバイスを使えなかった |
| 音量 100% 以外の警告 | SSL 2 MKII はソフトウェア音量のため、警告ではなく「排他モードではかからない」と表示（Windows の音量 90%） |
| SSL のコントロールパネルでレートを 96 → 44.1 kHz に変えて `--formats` | 排他モードで受け付けるのが 44.1 kHz だけに変わった（16bit、24bit を 32bit コンテナに入れた形、32bit）。Windows の既定の形式も 44.1 kHz / 32bit に変わった |

### S1：分かったこと

- **SSL 2 MKII のドライバーは、コントロールパネルで設定したレートに固定する。** 排他 WASAPI からはレートを切り替えられない。この機器で曲ごとにレートを切り替えるには ASIO（1-4）が要る。WASAPI でレートが合わないときは、「SSL の設定でレートを ○○ kHz にしてください」と案内できるとよい（1-1）。
- **レートを変えると、SSL のエンドポイント ID が変わった**（96 kHz で `{181ab626-…}`、44.1 kHz で `{9ffad2c9-…}`。96 kHz に戻すと元の ID に戻った）。一覧の並び順も変わった。出力デバイスの選択を保存するときは、ID だけに頼らず、名前でも探し直す必要がある（1-1）。
- 24bit は、どのレートでも 32bit コンテナでしか受け付けない。コンテナの詰め替え（値は変えない）を入れておいたのは正しかった。

### S3：画面の骨組み（2026-11-08）

- 構成：JUCE の `WebBrowserComponent`（WebView2、SDK 1.0.3485.44 を静的リンク）に、`ui/`（Vite 8 + TypeScript）の画面を表示する。ビルド版は exe の隣の `ui/` フォルダーから読み込み、`--dev-server` を付けると Vite の開発サーバーから読み込む。
- 橋渡し：画面 → エンジンは JUCE のネイティブ関数（`openFile`、`play`、`stop`、`seek`、`getStatus`、`uiReady`）。エンジン → 画面は `playbackStatus` イベント（10 回/秒まで、変化したときだけ）。
- エンジン：`Player` が別スレッドで原音経路を再生する。シークは出力を開き直さず、次の読み込みで位置を変える（データは原音のまま）。
- 自動テスト（ctest の `smoke` ラベル）：
  - `app_smoke_test`：WebView2 が起動し、ビルド版の画面が読み込まれ、画面からエンジンへの呼び出しが届く。
  - `app_self_test`：画面の JavaScript が、再生 → 位置の通知 → 半分へシーク → 最後まで → 再生 → 停止 を実際のネイティブ関数で行い、ダミー出力に届いたバイト列が元の PCM の先頭部分と一致することをアプリが確かめる。
  - 開発サーバーから読み込む場合も、手動で同じ2つを実行して通ることを確認した（Vite が動いている必要があるため ctest には入れていない）。
- 画面の文言（日本語）とエラーの説明は `ui/src/messages.ts`。WASAPI でレートが合わないときは「デバイスの設定でレートを ○○ kHz にすると再生できる場合があります」と案内する。
- 不具合（修正済み）：最初の版は、WebView の大きさが 0×0 のままでウィンドウが真っ黒だった（画面の JavaScript は動いていたので自動テストは通っていた）。自己テストに「画面が WebView の大きさを埋めているか」の確認を足した。
- 実機での確認（ユーザー、Release 版）：画面が表示される。`sine96_m40.wav`（96 kHz）を「ファイルを開く」から選んで再生できた。SSL を 48 kHz などにすると、レートの案内文が表示された。

### 1-1：出力デバイスと形式の確認（2026-11-08）

- **形式の判定**（`engine/output/format_probe`）：出力は「この形式をそのまま受け付けるか」だけを答え、断られた理由は近い形式を試して共通の関数で判定する。理由は、レート（SampleRate）、ビット深度（BitDepth）、浮動小数点と整数の違い（SampleType）、チャンネル数（Channels）の4つ。あわせて「今受け付けるレート」を返す。WASAPI とダミー出力は同じ関数を使う。
- **テスト**：S1 で記録した実機の受け付け方（SSL 2 MKII の 96 kHz 時、HDMI の 44.1/48 kHz 16bit、浮動小数点だけのデバイス）を写した架空のデバイスで、非対応の組み合わせごとに理由と受け付けるレートを確かめる。Player を通しても同じ理由が返ることを確かめる。
- **案内**：レートが合わないとき、画面と `ap_play` は「このデバイスが今受け付けるのは 96 kHz です。デバイスの設定でレートを 44.1 kHz にすると再生できる場合があります」と出す。実機（SSL、96 kHz 設定）で `ap_play --check` の表示を確認した。
- **デバイスの選び直し**（`engine/output/device_selection`）：保存した {ID, 名前} から、ID → 名前 → 既定のデバイスの順に探し、どれで見つけたかを返す（SSL のようにレートで ID が変わるドライバーへの対策）。画面で使うのは 6-3。
- デバイスの抜き差し・既定の変更の通知は 1-2 に回した。

### 1-2：再生キュー、ギャップレス、レートの切り替え（2026-11-08）

- **再生キュー**（`Player::setQueue`）：曲は必要になったときに開く。今の曲を再生している間に、次の曲を裏で開いておく（今は曲全体をメモリーに読む。先読みの仕組みは 1-3）。
- **ギャップレス**：次の曲が今の曲と**まったく同じ形式**なら、同じ出力のまま、今の曲の最後のフレームの直後に次の曲の最初のフレームを続ける。
- **レートの切り替え**：形式が違えば、今の曲を最後まで鳴らしてから出力を閉じ、次の曲の形式で開き直す。切り替えを「どの曲からどの曲へ」「形式」「データが途切れてから次の曲のデータを送り始めるまでの時間（無音の上限の目安）」として記録し、画面と `ap_play` に表示する。
- 次の曲をデバイスが受け付けない、または開けない場合は、そこで止めて理由を表示する。
- **自動テスト**：同じ形式の曲が続くと、出力が入力をつなげたものと1バイト残らず一致し、出力は1回しか開かれない（ギャップ 0、重なりなし）。形式が違えば開き直し、切り替えが記録される。混在、エラー、停止と再開も確かめる。
- **デバイスの通知**（`DeviceWatcher`）：出力デバイスの追加・削除・状態の変化・既定の変更を受け取る。`ap_play --watch` で表示できる。画面で使うのは 6-3。
- **要実機確認（つなぎ目の試聴）**：`build/gapless-check/` に、96 kHz・1 kHz・−40 dBFS・5 秒のファイルを3つ用意した。`1_tone_a` と `2_tone_b` は、続けると切れ目のない1本のサイン波になる。`3_click_reference` は位相を 90° ずらしたもので、`1_tone_a` に続けると継ぎ目で波形が飛ぶ（聞こえ方の比較用）。
  - 結果（SSL 2 MKII、96 kHz、`ap_play`）：`1_tone_a` → `2_tone_b` は、継ぎ目で「プツッ」と鳴らなかった（ユーザー確認）。ソフト側の記録は「ギャップレス」。比較用の `1_tone_a` → `3_click_reference` は、継ぎ目で「プツッ」と鳴った（ユーザー確認）。つまり、この条件で継ぎ目の乱れは聞き取れる。そのうえで 1 → 2 では鳴らなかったので、ギャップレスの再生は実機でも成り立っている。

### 1-3：先読み、スレッド優先度、音切れの記録（2026-11-08）

- **先読み**（`PrefetchingSource`）：専用のスレッドがファイルを先に読み、リングバッファー（既定で約2秒分）にためる。再生スレッドはそこから取り出すだけで、ディスクを待たない。再生の前にバッファーを満たしておく。目的は音切れを防ぐことで、音質向上とは謳わない。
  - 先読みが間に合わなかったときは、足りない分を無音で埋め、「ファイルの読み込みの遅れ」として回数とフレーム数を記録する（黙って隠さない）。
  - 再生中のシークは、読み込み側が新しい位置から埋め直すまでの短い間だけ無音になる（音切れには数えない）。再生していないときのシークと最初からの再生し直しは、データがそろうまで待ってから始める。
- **デバイス側の音切れ**：WASAPI では、デバイスがデータを求めてから1周期以内に渡せなかったバッファーを「デバイスへの受け渡しの遅れ」として数える。要求ごとに測るので、デバイスの時計と PC の時計のずれが長時間で積み重ならない。デバイスの応答なし（タイムアウト）も数える。
- **スレッド優先度**：再生スレッドは MMCSS「Pro Audio」。実際に効いたかを記録し、画面と `ap_play` に表示する。先読みのスレッドは通常より一段上の優先度。
- **自動テスト**：再生スレッドを止めるとデバイス側の遅れとして記録され、データは変わらない。ディスクの遅れが先読みより長いと読み込み側の音切れとして記録され、出力はちょうどその分だけ長くなる。CPU の全コアに負荷をかけた状態でも、記録と出力が食い違わない（音切れ 0 なら出力は入力と一致）。参考：負荷をかけた Debug 版では、優先度が普通のダミー出力が遅れ、15 回として記録された。
- **要実機確認**：`ap_play --stress N` で CPU に負荷をかけながら SSL 2 MKII で再生し、音切れの回数と、聞こえ方が合っているかを確かめる。
  - 結果（SSL 2 MKII、96 kHz、`1_tone_a` → `2_tone_b`、24 論理プロセッサーの PC）：負荷なし・`--stress 48` のどちらも、音切れ 0 回、MMCSS（Pro Audio）が効いた。聞こえ方も2回とも途切れなし（ユーザー確認）。
  - 検出の確認（`ap_play --inject-stall 3:50`：1 曲目の 3 秒で再生スレッドを 50 ms 止める）：3 秒のところで途切れが聞こえ（ユーザー確認）、表示は 3.0 → 3.1 秒で 0 → 1 回、集計は「デバイスへの受け渡しの遅れ 1、ファイルの読み込みの遅れ 0」。聞こえた回数と記録が一致した。
  - 途中で見つけて直した不具合：既定のバッファーの大きさが読み込みの単位で割り切れないと、先読みが満杯にならず、曲を開くたび（停止中のシークのたび）に 5 秒の待ち時間切れまで待っていた。既定の大きさで確かめるテストを足して直した。

### 1-4：ASIO 出力（2026-11-08）

- **SDK**：Steinberg ASIO SDK 2.3.4 の GPLv3 版。ホストに必要なヘッダー3つと LICENSE などを `third_party/asiosdk/` に無改変で同梱した（`VENDORED.md`）。ロゴは使わない。
- **ASIO 出力**（`AsioOutput`）：ドライバーは COM で直接作り（SDK の `asio.cpp` の全体共有の仕組みは使わない）、専用の STA スレッド（メッセージを処理するループと、隠しウィンドウ付き）からだけ呼ぶ。

### 1-5：DSF/DFF の読み込みと DoP 出力（2026-11-08）

- **読み込み**：DSF（1 bit/サンプルは LSB 先頭、チャンネルごとの区画）と DFF（非圧縮の DSDIFF。DST 圧縮は断る）を、内部では「MSB 先頭、1バイトずつチャンネル交互」の形にそろえる。DSF のビットの並べ替えは順番の入れ替えだけで、情報は失わない。
- **DoP**（v1.1）：24bit の PCM の上位 8bit を目印（0x05 と 0xFA をフレームごとに交互、同じフレームの全チャンネルで同じ値）、下位 16bit を DSD の 16 ビット分（時間が早いほうが上位）にする。PCM のレートは DSD のレート ÷ 16（DSD64 → 176.4 kHz、DSD128 → 352.8 kHz、DSD256 → 705.6 kHz）。出力層には普通の PCM として渡す（WASAPI 排他・ASIO・32bit コンテナへの詰め替えも、目印は崩れない）。
- **曲のつなぎ目**：各曲を偶数フレームにそろえる（足りない分は DSD の無音 0x69）。こうすると、ギャップレスでつないだときに目印の交互が途切れない。
- **安全のため、DoP は既定で送らない**。DoP に対応していない DAC では大きなノイズ（目印などが音になる）になり、DAC が対応しているかはアプリから分からないため。出力ごとに「DoP を使う」をオンにしたときだけ送る（`ap_play --dop`、アプリは今は `--allow-dop`。設定画面は 6-3）。PCM の曲と DoP の曲は、形式が同じでもつながずに開き直す（確認をすり抜けないように。DAC のモードの切り替えのためにも）。
- **画面**：入力を「DSD64（2.8224 MHz）/ 2ch（DSF）」のように DSD として表示し、処理を「なし（DoP の経路では処理をかけられません）」にする。DoP で送っている間は「DoP に対応していない DAC では、大きなノイズになります」と注意を出す。
- **自動テスト**（完了条件）：読み込みがビット単位で正しいこと（DSF のビットの向きは仕様の値で固定）、DoP の目印が交互で全チャンネル共通なこと、DSD のビットの順番、奇数の長さの埋め方、つなぎ目で目印が続くこと、シーク、DSD64/128/256 と 48 kHz 系のレート、DSF と DFF から同じ DoP が出ること、Player とダミー出力を通した並び（32bit コンテナへの詰め替え込み）、DoP を使う設定がオフのときに断ること。
- **テスト信号**：`ap_signalgen dsd` で、1 kHz のサイン波を2次のΔΣ変調した DSD を DSF/DFF で書き出せる（0 dB = 変調度 50%）。
- **要実機確認（DoP 対応の DAC が手に入ってから）**：`ap_signalgen dsd --out tone.dsf` で作ったファイルを `ap_play tone.dsf --dop`（または ASIO で `--asio N --dop`）で再生し、DAC の表示が DSD64 になるか、1 kHz の音が聞こえるかを確かめる。**SSL 2 MKII は DoP に対応していないので、DoP を送らないこと。**
- メモ：Vite の開発サーバーで画面を開くと、コンソールに「blob から worker を作ろうとして CSP に止められた」というエラーが出ることがある。こちらのコードは worker を作っていない。アプリ（WebView2）での自己テストは通る。開発サーバー側の機能に影響があるかは未確認。
- DoP の実機確認用に FiiO KA11（Type-C）を用意した（2026-11-08 注文）。表示灯は青 = PCM 48 kHz 以下、黄 = PCM 48 kHz 超、緑 = DSD（FiiO の公式サポート）。DoP の DSD64 は PCM 176.4 kHz として届くので、緑なら DSD として受けている、黄なら解釈していない（すぐ止める）。FiiO のドライバーを入れると ASIO も使え、仕様（DSD256、PCM は 384 kHz まで）からするとネイティブ DSD（フェーズ2）にも使える見込み（未確認）。
- **実機確認（2026-11-10、FiiO KA11、Windows 標準のドライバー・排他 WASAPI）**：通った。
  - `ap_play --formats --device N`：KA11 は 44.1〜384 kHz のすべてで 16bit・24bit（32bit コンテナ）・32bit を受け付け、24bit（3 バイト）と 32bit 浮動小数点は受け付けない。DSD64 の DoP は 176.4 kHz の 24bit を 32bit コンテナに詰め替えて送る。
  - 先にダミー出力で確かめた：出力のハッシュが入力と一致し、882,000 フレーム（5 秒）すべてで目印が 0x05 / 0xFA の交互（左右同じ）。
  - `ap_signalgen dsd --level -40 --seconds 15` の DSF を `ap_play --dop --device N` で再生：**表示灯は緑（DSD）**、1 kHz の澄んだ音が聞こえた（ユーザーが確認。Windows の音量 32%）。音切れ 0 回、MMCSS（Pro Audio）が効いた。1 回の受け渡しは 1764 フレーム（10 ms）。
  - DFF は自動テストで DSF と同じ DoP が出ることを確かめている（実機では DSF だけ流した）。
  - 同じ日に FiiO のドライバー（FiiO ASIO Driver 版 1552、形式 Int32LSB、44.1〜384 kHz）を入れて続けた。入れた後も WASAPI で受け付ける形式は変わらない。DSD128 もダミー出力で一致、目印の乱れなし（15 秒、5,292,000 フレーム）を確かめてから、−40 dB・15 秒の DSF を3通り流した：**WASAPI で DSD128（352.8 kHz）、ASIO で DSD64（176.4 kHz）、ASIO で DSD128（352.8 kHz）。3通りとも表示灯は緑、1 kHz の澄んだ音**（ユーザーが確認）。音切れ 0 回。ASIO では曲ごとにドライバーのレートを切り替え、バッファーはレートに合わせて変わる（176.4 kHz で 2048、352.8 kHz で 4096 フレーム。どちらも 11.6 ms）。聞こえる音量は WASAPI と ASIO で同じくらい（Windows の音量 37%。KA11 は ASIO でも Windows の音量が効いているように見えるが、測ってはいない）。
  - 未確認：DSD256 の DoP（705.6 kHz。KA11 は PCM 384 kHz までなので DoP では送れない）、ネイティブ DSD（フェーズ2）。

### 1-6：再生経路の記録（2026-11-08）

- **何を記録するか**：今の曲の経路を、各段が「実際にしたこと」だけで組み立てる（推測や判定は入れない）。エンジンの `PlayerStatus::path`（`SignalPath`）に、入力・処理・出力をまとめる。
  - **入力**：ファイルの種類（WAV / DSF / DFF）、読んだ形式、DSD を DoP で包んでいるか（DSD のレート）。
  - **処理**：フェーズ1は原音経路だけなので「なし」。段ごとの記録（音量、ReplayGain、EQ、リサンプラー、ディザ）は M3 で足す。
  - **出力**：各出力が開いたあとに自分で報告する（`AudioOutput::pathInfo()`）。
    - 共通：方式（排他 WASAPI / ASIO / ダミー出力）、デバイス名、受け取った形式、1回に送るフレーム数（周期・バッファー）、サンプルの置き方（そのまま／チャンネルごとにコピー／32bit の枠の下位に右詰め）。
    - WASAPI：イベント駆動であること、開いたときの Windows の音量（値、ミュート、デバイスの中でかかる音量か）。音量の操作がないデバイスでは何も書かない。
    - ASIO：ドライバーが返した名前と版、サンプル形式（`Int32LSB24` など）、開くときにレートを切り替えたか（切り替える前のレート）。
- **BIT-PERFECT の判定はしない**。判定と根拠の表示は 4-2・4-3 で、この記録を使って行う。
- **画面**：経路の欄に「出力の方式」と「Windows の音量」の行を足した。これまで出力デバイス名に固定で付けていた「（排他 WASAPI）」は外し、実際の方式を表示する（ASIO で再生しても「排他 WASAPI」と出ていた）。ASIO でレートを切り替えたときは、送る形式の行に「ドライバーのレートを 96 kHz → 44.1 kHz に切り替えました」と出す。出力の確認画面（SIGNAL PATH）は 6-4。
- `ap_play` も、送る形式のあとに「出力の方式」と「処理」を表示する。
- **自動テスト**（完了条件）：ダミー出力が開いている間だけ経路を報告すること、WASAPI の経路をデバイスが返した値から組み立てること（音量の扱いを含む）、WAV をそのまま送る・32bit コンテナに詰め替える・DSF を DoP で送るときの経路、偽の ASIO ドライバーで右詰めの形式（Int32LSB24）とそのままの形式（Int32LSB）、ドライバー名・版、レートの切り替えが記録されること、新しい曲の列で経路が消えること。画面の文言（方式、右詰めの説明、レートの切り替え、Windows の音量の4通り）。
- **実機での確認**（SSL 2 MKII、`ap_play`、1 kHz −40 dBFS のサイン波を3秒ずつ、音量は下げてもらった）：
  - WASAPI（SSL はコントロールパネルで 48 kHz）：48 kHz/24bit を再生。「出力の方式：排他 WASAPI（イベント駆動）・1 回に 480 フレーム（10.00 ms）」、Windows の音量は 100%（ソフトウェア音量）、送る形式は 32bit コンテナへの詰め替え。音切れ 0 回。
  - ASIO（SSL ASIO Driver 1、版 1352、最初のレート 48 kHz）：44.1 → 96 → 48 kHz の3曲を続けて再生。各曲で「ドライバーの形式 Int32LSB」と「ドライバーのレートを 48 → 44.1 / 44.1 → 96 / 96 → 48 kHz に切り替えた」が出た。切り替えは約 171 ms と約 162 ms、音切れ 0 回。
  - **分かったこと：SSL の ASIO ドライバーは、レートによってバッファーの大きさを変える**（44.1 / 48 kHz で 64 フレーム、96 kHz で 128 フレーム。どれも約 1.3〜1.5 ms）。ドライバーを読み込んだときの値ではなく、開くたびに読んだ値を記録しているので、表示もそのとおりに変わった。
  - Int32LSB はそのままの幅の形式なので「右詰め」の表示は出ない（右詰めの表示は偽のドライバーのテストでだけ確かめている）。

### 2-1：FLAC・WAV・AIFF の読み込み（2026-11-09）

- **FLAC**：libFLAC 1.5.0（BSD-3-Clause）でデコードする。C のライブラリだけを組み込み、コマンドラインのプログラム（GPL）、libFLAC++、Ogg 対応は作らない。
  - 整数のまま、元のビット数で出す。16/24/32bit 以外（12bit、20bit など）は、入る大きさの枠（16/24/32bit）の上位に詰め、「有効 20bit（24bit コンテナ）」のように記録する（WAV や WASAPI と同じ左詰め。値は変えない）。
  - スピーカーの割り当ては FLAC の決まり（1ch〜8ch）に従う。
  - **MD5 の照合**：FLAC はデコード後の音声データの MD5 を持っている。最初から最後まで途中でシークせずに読んだときだけ照合し、「一致」「不一致」を記録する。途中にシークしたら「照合できない」とし、最初に戻すと照合し直す。MD5 のないファイルは「照合用の値がない」とする。デコーダーがファイルの中の誤り（同期の喪失、CRC の不一致など）を報告したら、MD5 にかかわらず「誤りあり」とし、その数を出す。照合が合わなくても再生は止めない（結果を表示するだけ）。
  - ファイルの先頭に ID3v2 タグが付いた FLAC も開ける。
- **AIFF / AIFC**：自前で読む。AIFF はバイトの並びが逆（ビッグエンディアン）なので、サンプルごとに並びを入れ替えて渡す（値は変わらない）。AIFC は NONE・twos・in24・in32・sowt・23ni・42ni（整数）と fl32・fl64（浮動小数点）に対応し、圧縮されたもの（ulaw など）と 8bit は断る。3ch 以上はスピーカーの割り当てを「指定なし」にする（AIFF の並び順は WAV と違うため）。
- **WAV**：RF64 / BW64（4 GB を超える WAV）にも対応した。
- **開き方**：拡張子ではなく中身で形式を判断する（`detectAudioFile`）。アプリのファイル選択は .wav .flac .aif .aiff .aifc .dsf .dff。
- **画面と `ap_play`**：入力の行にファイルの種類（FLAC など）を出す。経路の欄に「ファイルの検証」の行を足し、照合の結果を出す。ギャップレスで先に進んだ曲の照合が合わなかったときは、「1 曲目は MD5 が一致しませんでした」と残す。
- **テスト信号**：`ap_signalgen` は `--out` の拡張子が `.flac` なら FLAC で書き出す（MD5 と 1 秒ごとのシーク表つき）。
- **自動テスト**（完了条件）：
  - FLAC：16/24/32bit × 44.1〜384 kHz で、デコード結果がエンコードした PCM と1バイト残らず一致し、MD5 が一致する。12bit・20bit の左詰め、1/2/6/8ch の割り当て、MD5 の書き換えを「不一致」と報告すること、壊したフレームを「誤りあり」と報告すること、MD5 なし、シーク（正確な位置、照合できない → 最初に戻すと照合）、ID3v2 付き、FLAC でないファイルを断ること。Player を通したとき、先に進んだ曲の照合結果が残ること。
  - AIFF / AIFC：16/24/32bit と 20bit、AIFC の型ごとの並び、SSND のオフセットや知らないチャンク、80bit のサンプルレート（8 kHz〜768 kHz）、シーク、途中で切れたファイル、断るべきファイル。
  - RF64 / BW64、中身による形式の判断（拡張子をわざと違えたファイル）。
  - **受け入れ基準（CLAUDE.md 5章）**：FLAC 入力（16/24/32bit × 44.1〜384 kHz × 3種類の信号）でダミー出力のハッシュが元の PCM と一致する。AIFF 入力も、並びを入れ替えた結果が元の PCM と一致する。
- **手持ちの音源での確認**（2026-11-09。ユーザーが用意した8ファイル。音源はリポジトリの外に出さないよう、`.git/info/exclude` で除外した）：
  - ダミー出力（音は出さない）で全ファイルを最後まで読み、**8ファイルすべてで出力のハッシュが入力と一致**した。FLAC：44.1 kHz/16bit（約7分、MD5 一致）、48 kHz/24bit（約6分、MD5 なし＝作ったソフトが記録していない）、192 kHz/24bit（MD5 一致）。AIFF：44.1 kHz/16bit、96 kHz/24bit。WAV：44.1 kHz/16bit、192 kHz/24bit、192 kHz/32bit。
  - AIFF の2つは、別に書いた簡単な読み込みプログラム（Python）の結果とも1バイト残らず一致した。
  - 同じ曲の組（AIF と WAV、FLAC と WAV）は出力が一致しなかったが、サンプルを比べると WAV のほうがどちらも約 13 dB 大きく、始まりの位置もずれていた。FLAC は MD5、AIFF は別の読み込みプログラムで正しく読めていることを確かめてあるので、ファイルそのものが別の設定で書き出されたものと判断した。
  - 実機（SSL 2 MKII、ASIO、音量は下げてもらった）：AIFF 44.1 kHz/16bit → FLAC 192 kHz/24bit → AIFF 96 kHz/24bit → WAV 192 kHz/32bit を続けて再生。4曲とも鳴り、SSL のレート表示も曲ごとに変わった（ユーザー確認）。切り替えは約 182 / 159 / 159 ms、音切れ 0 回。192 kHz では ASIO のバッファーが 256 フレームになった（約 1.3 ms。レートでバッファーの大きさを変える動きは 1-6 と同じ）。
- **途中で見つけて直した不具合（`ap_play --dummy`）**：最初は8ファイル中7ファイルで「不一致」になった。デコーダーの問題ではなく（FLAC の MD5 は一致していた）、ダミー出力がデバイスと違って「できるだけ速く」データを受け取るため、約2秒分の先読みを追い越し、先読みが足りない分を無音で埋めていた（デバイスのための正しい動きで、音切れとして記録されていた）。これまで確かめたファイルは1秒以下で、先読みに収まっていたので表に出なかった。`--dummy` のときは先読みを使わずファイルを直接読むようにし、無音で埋めたときは不一致の理由を表示するようにした。自動テストの受け入れ基準は先読みを通さないので、影響はない。

### 2-2：ALAC（2026-11-09）

- **デコーダー**：Apple の公開版（macosforge/alac、Apache 2.0）のデコーダーを `third_party/alac/` に同梱した。
  - **公開版は 2011 年から直されておらず**、同じコードを使った MediaTek・Qualcomm のデコーダーで、細工した音声ファイルでメモリーを壊せる脆弱性が見つかっている（Check Point「ALHACK」、CVE-2021-0674 / 0675 / 30351）。原因は、ファイルの中の値を確かめずに使っていること。
  - このプレイヤーはどこから来たファイルでも開くので、**値を使う前にすべて確かめる変更を 10 か所入れた**（ファイルの先頭の設定、フレームごとのサンプル数、各チャンネルのビット数、パケットの終わりを超えて読まないこと、など）。一覧と元のファイルのハッシュは `third_party/alac/VENDORED.md`。手を入れたのは2ファイルだけで、ほかは上流と1バイトも違わない。
  - 上流の `codec/` には Apple Public Source License の本文も置かれているが、使うファイルはどれも Apache 2.0 のヘッダーを持ち、それを参照していないので同梱していない。
  - MSVC の x64 では、上流のバイト順の判定が働かない（`__x86_64__` は GCC の記号）。ソースは変えず、`TARGET_OS_WIN32` を定義して正しい側を選ばせている。
- **入れ物**：MP4（.m4a）を自前で読む（`mp4_reader`）。最初の音声トラックの、各パケットの位置・大きさ・フレーム数、コーデックの設定、編集リスト（最初の空でない編集：先頭を飛ばす量と長さ）を取り出す。大きさや数はすべて、入っている箱とファイルの大きさで確かめる。.m4a でも中身が AAC のものは「2-4 で対応」と理由を付けて断る。.caf は対応しない（使う人が少ないため。必要なら後で）。
- **出力**：整数のまま、元のビット数で出す。20bit は 24bit の枠の上位に詰める（FLAC と同じ）。3ch 以上はスピーカーの割り当てを「指定なし」にする（ALAC の並びは中央が先頭で、WAV と違う）。照合用の値はないので、ファイルの検証は「照合用の値なし」。デコーダーが断ったパケットは同じ長さの無音にし、「誤りあり」として数える。
- **分かったこと：Windows の ALAC エンコーダーは、曲の本当の長さを残さない**。最後のパケットを無音で 4096 フレームまで埋め、表にも「全部 4096 フレーム」と書く（トラックの長さも同じ）。そのため Windows で作った ALAC は、最大で約 0.09 秒（44.1 kHz）の無音が曲の終わりに付き、ギャップレスにはならない。ファイルにそう入っているので、このプレイヤーも Windows のデコーダーと同じ長さで再生する。Apple の道具で作ったファイルは、最後のパケットに本当のフレーム数が入っているので、ちょうどの長さで再生する。
- **テスト用のファイル**は2通りで作った：
  - Apple のエンコーダー（テスト専用。同じリポジトリの、手を入れていないもの）と、テスト用の小さな MP4 書き出し。Apple の道具と同じく、最後のパケットに本当の長さが入る。16/20/24/32bit、44.1〜384 kHz、1〜8ch。
  - Windows の ALAC エンコーダー（Apple のコードとは別の実装）。16/24/32bit、44.1〜192 kHz（352.8 / 384 kHz は受け付けなかった）。
- **自動テスト**（完了条件）：
  - デコード結果が元の PCM と1バイト残らず一致し、長さもちょうど（16/20/24/32bit × 44.1〜384 kHz）。圧縮できない信号（そのまま格納する経路）、1〜8ch、編集リスト、シーク。
  - Windows で作ったファイル：埋められた無音までを含めて、Windows のデコーダーの結果と1バイト残らず一致。Apple のエンコーダーで作ったファイルも、Windows のデコーダーの結果と一致。
  - 危険なファイル：ありえない設定値（フレーム長 0 や 2^31、ビット数 8 や 33、チャンネル数 0 や 9 など）を断ること。ALHACK と同じ形（フレームに書かれたサンプル数がフレーム長を超える）を、小さいパケットと大きいパケットの両方で作り、断ること。パケットのビットをでたらめに壊したファイル（600 通り）で落ちず、誤りが数えられること。MP4 の表の壊れ（数が巨大、位置がファイルの外など）を断ること。途中で切れたファイル。
  - **AddressSanitizer**（メモリーの誤った読み書きを見つける仕組み）を入れたビルド（`vs2022-asan`）でも、全テスト（182 件）が通った。

### 2-3：MP3（2026-11-09）

- **デコーダー**：mpg123 1.33.7（LGPL 2.1）を DLL（`mpg123.dll`）として組み込んだ。公式のソース配布をハッシュで固定し、mpg123 の CMake でデコードのライブラリだけを作る。アセンブラーを使わない C だけのデコーダーにした（どの CPU でも同じ結果になるので、テストで値を確かめられる）。DLL はアプリ・`ap_play`・テストの exe の隣にビルドのたびに置き、MSIX の試作パッケージにも入れた。
- **浮動小数点のまま**（CLAUDE.md：非可逆は浮動小数点でデコード）：mpg123 の計算と出力はどちらも 32bit 浮動小数点。整数に丸めないので、デコードした波形が 1.0（0 dBFS）を超えるところもそのまま残る（クリップしない）。64bit で計算しても違いを測れないので、そうはしていない。
- **実機での再生は M3 で**（ユーザーと相談して決めた）：手元のデバイスは、どれも排他モードと ASIO では整数の形式しか受け付けない。浮動小数点をディザをかけて整数にするのは処理経路（M3 の 3-1・3-2）の仕事なので、それまでは整数しか受け付けないデバイスでは「浮動小数点の形式に対応していません。処理経路ができるまで再生できません（勝手に変換はしません）」と理由を出して断る。浮動小数点を受け付けるデバイスなら、今でもそのまま送れる。`ap_play --formats` に「32bit 浮動小数点」の列を足した（KA11 などで確かめるため）。
- **ギャップレス**：LAME タグに書かれたエンコーダーの遅延と末尾の埋め草を mpg123 が取り除く。開くときにファイルを読み通して、長さをちょうどに決める。LAME タグのない MP3 は、何を取り除けばよいかがファイルに書かれていないので、元の音より長くなる（テストで確かめた）。
- **シーク**：位置はちょうど。値は、頭から読んだときと浮動小数点の丸めの範囲で一致する（最大 1.2×10⁻⁷、約 −138 dBFS、24bit の1段ぶん）。1ビット単位で一致しないのは、mpg123 の合成フィルターが書き込む輪状のバッファーの開始位置がフレームごとに進み、シークのあとは別の位置から始まるため、同じ足し算の順番が変わって最後の桁の丸めが変わるから。位置がずれていれば、差は信号そのものの大きさになる。
- **テスト用のファイル**：LAME 3.100（LGPL）をテスト専用にビルドして作った（配布物には含まない）。LAME タグを書くエンコーダーが要るため。
- **自動テスト**（完了条件）：
  - 長さがちょうどで、位置がずれない（MPEG-1・2・2.5 の 8 通りのサンプルレート × モノラル・ステレオ、VBR）。
  - **Windows の MP3 デコーダー（別の実装）との差**：3通りのレート × CBR 128 / CBR 320 / VBR × 3種類の信号（音楽ふう・0 dBFS 近くの矩形波・−60 dBFS のサイン波）の27通りで、差の RMS が −94〜−99 dBFS、最大が −89.8〜−90.4 dBFS。基準は「RMS −90 dBFS 未満、最大 −70 dBFS 未満」にした。差の最大がほぼちょうど −90.3 dBFS（1/32768）なのは、Windows のデコーダーが内部で 16bit に丸めているためと見られる（比べているのは主に相手側の分解能）。
  - **クリップしない**：0 dBFS 近くの矩形波で、こちらの出力には 1.0 を超える値が残る。Windows のデコーダーは最大がちょうど 1.0000 で、クリップしている（比べるときは、こちらの値を同じく ±1.0 に収めて比べた）。
  - ギャップレス：1本の信号を2つに分けてそれぞれ MP3 にし、続けて再生すると、長さが元とちょうど同じで、後ろの曲の始まりもずれない。
  - 整数しか受け付けない出力では、理由（浮動小数点）を付けて断り、変換しない。
  - 中身による形式の判断（ID3v2 付きも）、日本語のファイル名、壊れたファイル・MP3 でないファイルで落ちないこと。AddressSanitizer のビルドでも通した。
  - **受け入れ基準（CLAUDE.md 5章）**：「非可逆デコード：リファレンスデコーダーとの差が許容範囲内で、クリップがない」を、上の27通りで自動テストにした（`tests/acceptance/lossy_test.cpp`）。
- **手持ちの MP3 での確認**（2026-11-09、ユーザーが用意した3つ。音は出さない）：

  | Nuendo 320 kbps | Nuendo の書き出し | なし | 同上 | 同上 |

  - Nuendo の MP3 は遅延の情報を書かないので、曲の頭に約 27 ms の無音が付き、長さも合わない（ファイルにそう入っている。Windows のデコーダーでも同じく長い）。
  - Nuendo の MP3 は、音量が同じ時に書き出した AIF と同じ（WAV より約 13.8 dB 小さい）だが、位置を合わせても AIF との相関は 0.83 しかなく、同じ音の MP3 とは言えなかった（320 kbps なら 0.999 程度になるはず）。書き出しの設定か処理が違うものと見られる。デコーダーについては、Windows のデコーダーとの差がほかのファイルと同じ水準なので、問題はない。
  - 実際のファイルを Windows のデコーダーと元の WAV に照らす確認は、テスト（`[.probe]`、環境変数 `AP_PROBE_IN` と `AP_PROBE_WAV`）として残した。
- **要実機確認**：実際に鳴らすのは、M3 で処理経路（ディザをかけて整数にする）ができてから、SSL 2 MKII で。
- 対象外：iTunes で作った MP3 の iTunSMPB（もう1つの長さの記録方法）。mpg123 は読まず、2-4 でも AAC だけに使った。iTunes で作った MP3 が手に入ったら、必要か確かめる。

### 2-4：AAC（2026-11-09）

- **デコーダー**：CLAUDE.md のとおり AAC のデコーダーは同梱せず、Windows の AAC デコーダー（Media Foundation の変換部品）を呼ぶ。.m4a は 2-2 の自前の読み込みで開き、パケットを1つずつデコーダーに直接渡す（曲の頭と終わりの削り方、シークをこちらで正確に決めるため）。出力は 32bit 浮動小数点（MP3 と同じ。実機での再生は M3 で）。
- **ギャップレス**：エンコーダーが頭に足したサンプル（priming）と末尾の埋め草を取り除く。編集リスト（elst）があればそれを、なければ iTunes の iTunSMPB を使う。どちらもなければ、何を取り除けばよいかがファイルに書かれていないので、デコードしたものを全部再生する。HE-AAC のように出力のレートが時間の単位の倍数になる場合も、その倍率で数え直す。
- **シーク**：AAC のフレームは前のフレームと重なっているので、目的の位置の2パケット前からデコードし直し、目的の位置より前の出力は捨てる。
- **分かったこと**：
  - **Windows の AAC エンコーダーは、elst も iTunSMPB も書かない**。ただし、Windows のエンコーダーで作って Windows のデコーダーで戻すと、priming は 0 フレームで、最後に 1 パケット未満の埋め草（543〜935 フレーム）が付くだけだった。
  - **Windows の AAC デコーダーはクリップしない**：0 dBFS 近くの矩形波で、1.0 を超える値がそのまま残った（最大 1.26）。MP3 のデコーダー（16bit に丸め、1.0 で切る）とは違う。
  - **Windows の AAC デコーダーは、壊れたデータを報告しない**：パケットを壊した 120 通りで、デコーダーからの誤りの報告は 0 回だった（誤りを黙って補うと見られる）。落ちることはなく、AddressSanitizer のビルドでも通った。
- **自動テスト**（完了条件）：
  - Windows のエンコーダーで作ったファイル（elst も iTunSMPB もない）：デコードしたもの全部を再生する（埋め草の分だけ長い）。
  - elst と iTunSMPB で頭を 0・1・1024・2112 フレーム、終わりを 777 フレーム削る指定をしたファイルで、削らずにデコードしたものの指定の範囲と1ビット違わず一致すること。priming を測った値で書き込んだファイルでは、長さが元とちょうど同じで、ずれが 0 になること。
  - Windows 自身のファイル読み取り（Media Foundation のソースリーダー）と、長さ・位置・値が完全に一致すること（デコーダーは同じなので、こちらの入れ物の読み方とパケットの渡し方の確認）。
  - シーク：位置がちょうどで、値も1ビット違わず一致（差 0）。
  - ギャップレス：1本の信号を2つに分けたファイルを続けて再生すると、長さが元と同じで、後ろの曲の始まりもずれない。
  - 整数しか受け付けない出力では、浮動小数点の理由を付けて断る。
- **「リファレンスデコーダーとの差」について**：AAC は CLAUDE.md の決まりで Windows のデコーダーそのものを使うので、別の実装との差は測っていない。必要なら、テスト専用に別のデコーダー（faad2 など）を入れて比べられる。
- **要実機確認**：
  - **Apple（iTunes / ミュージック）や FFmpeg で作った AAC**（iTunSMPB の priming は 2112、FFmpeg の elst は 1024 が普通）を、元の WAV と比べて、長さがちょうどで、ずれが 0 になるかを確かめる。Windows のデコーダーの出力の始まりが、これらのエンコーダーの priming の数え方と合っているかは、この確認でしか分からない。
  - 実際に鳴らすのは、M3 で処理経路ができてから。
- **確認（2026-11-10）**：
  - プローブ（`ap_engine_signal_tests "Probe: a real AAC against Windows' reader and its source WAV"`、`AP_PROBE_IN` に .m4a、`AP_PROBE_WAV` に元の 16bit WAV）を足した。
  - **iTunes で作った AAC**（`16-441 -AAC - iTunes.m4a`、元は 11 秒の 16bit WAV）：edit list なし、iTunSMPB はプライミング 2112・余り 740・元の長さ 486,620 フレーム。iTunSMPB で削った結果は 486,620 フレームで、**元の WAV と長さの差 0、ずれ 0**。SN 比 31.7 dB（2-3 の MP3 の 31.9 dB と同じくらい）、ピーク −3.07 dBFS、デコードのエラー 0。Windows のデコーダーの出力の始まりが Apple の priming の数え方と合っていることが分かった。Windows 自身のファイル読み込み（Media Foundation）は iTunSMPB を使わないので、頭に 2112 フレーム多く出る（こちらの読み込みとのずれ 2112）。
  - 同じファイルを KA11 で再生（3-2 の処理経路で 32bit 整数・TPDF ディザ）：普通に聞こえた（ユーザーが確認）。音切れ 0 回。
  - FFmpeg で作ったものは ADTS（`.aac`、MP4 に入っていない）だった。ADTS には頭と末尾を削る情報を入れる場所がないので、どのプレーヤーでも正確な長さにはできない。今は .m4a だけに対応（`.aac` は読めないと表示する）。FFmpeg 製は `.m4a` で書き出したもの（`ffmpeg -i in.wav -c:a aac out.m4a`、edit list でプライミング 1024 を書く）で確かめる（U）。ADTS の .aac を読めるようにするかは、必要になったら決める。

### 3-1：64bit の処理経路と完全バイパスの判定（2026-11-10）

- **処理の段**（`ProcessingStage`）：64bit 浮動小数点（フルスケール = ±1.0、インターリーブ）を、その場で書き換える。「今は何もしない状態か」（`isIdentity()`、例：音量 100%）を返す。処理の列（`ProcessingChain`）は段を決まった順に並べ、何もしない段は飛ばす。実際の段（音量、ReplayGain、EQ など）は 3-2 以降で入れる。
- **完全バイパス**：出力を開くときに、すべての段が何もしない状態なら、今までの一本道（原音経路）をそのまま使う。処理のコードは1行も通らない。DoP の曲は、段が有効でも処理しない（Player の曲の列からも DoP かどうかが伝わるようにした）。
- **変換**：16/24/32bit の整数（コンテナの幅で読み、2^(コンテナのビット数−1) で割る）と 32/64bit の浮動小数点を 64bit 浮動小数点にし、出力の形式に戻す。整数は有効ビット数で最も近い値に丸め（ちょうど中間は偶数へ）、範囲の外は端の値にそろえて数える。コンテナの下位ビットは 0。浮動小数点の出力はそろえない（範囲の外は数えるだけ）。NaN は 0 にする。**ディザはまだかけない**（3-2 で、量子化の前に入れる）。
- **処理経路の出力形式**（ユーザーと決めた）：レートとチャンネル数は曲のまま。サンプル形式は、デバイスが受け付ける中でいちばん細かいもの：32bit 整数 → 24bit（32bit コンテナ）→ 24bit → 16bit → 32bit 浮動小数点（整数を受け付けないデバイスだけ）。KA11 と SSL 2 MKII は 32bit 整数になる。
- **置き場所**：再生スレッド（ASIO ではドライバーのスレッド）で、先読みの後に処理する（音量の変更が先読みの分だけ遅れないように）。処理の間だけ FTZ/DAZ を有効にし、終わったら元に戻す（ドライバーのスレッドの設定を変えたままにしないため）。
- **経路の記録**：`SignalPath::processing` と、出力を開いたときに有効だった段の名前（`processingStages`）を記録する。範囲の外に出たサンプルの数を `PlaybackReport::overs` に数える（画面に出すのは 3-5 のリミッターの記録と一緒に）。
- **自動テスト**（完了条件）：
  - 受け入れ：何もしない段だけの列で、バイパスが成立し、出力が原音経路とバイト単位で一致する（16/24/32bit × 44.1〜384 kHz × ビットパターン・ISP 信号・1 kHz −90 dBFS の 72 通り）。同じ入力を処理経路に強制的に通して同じ形式で出しても一致する（変換だけでは値が変わらない）。
  - 単体：整数（16/24/32bit、24bit・16bit を広いコンテナに入れたもの）と浮動小数点が往復で変わらないこと、丸めと範囲の外の扱い、出力形式の選び方、処理経路でもギャップレスでつながること、段が有効なら値が変わること、FTZ/DAZ が処理中だけ効くこと、DoP を処理しないこと、Player の経路の記録。
- **申し送り（3-2）**：
  - 再生中にバイパスかどうかが変わったとき（例：原音モードで音量を 100% から下げた）は、今の位置で出力を開き直す（ユーザーと決めた。約 25 ms と DAC の合わせ直しの間だけ途切れる。途切れない切り替えは 3-7）。音量の段と一緒に作る。
  - 整数しか受け付けないデバイスで MP3・AAC を鳴らせるのは、ディザをかけて量子化する 3-2 から。3-1 の時点では、処理経路で浮動小数点を整数にする段は実際には動かない（実際の段がまだないため）。

### 3-2：デジタル音量と TPDF ディザ（2026-11-10）

- **TPDF ディザ**：整数に量子化するときだけ、±1 LSB（出力の有効ビット数での LSB）の三角分布の値を足してから丸める。浮動小数点の出力にはかけない。範囲の外のサンプルは、ディザを足す前の値で数える（フルスケール付近でディザのせいで数えないように）。乱数は xoshiro256**（パブリックドメイン）で、出力を開くたびに同じ種から始める（同じ入力なら同じ出力。テストを再現できる）。ノイズシェーピングはしない。
- **音量の段**（`VolumeStage`）：0 dB 以下（上げることはできない。上げるとクリップするため。ヘッドルームは 3-5 の ISP セーフの仕事）。−∞ でミュート。変えたときは 10 ms で直線的に移る（波形に段差を作らない）。0 dB で、移り終わったときだけ「何もしない」状態になる。出力を開いたときは移らずに、その時点の音量から始める。
- **再生中の切り替え**（3-1 でユーザーと決めた）：処理経路が要るかどうかが変わったら（音量を 100% から下げた、100% に戻して移り終わった）、今の位置で出力を開き直す。曲の切り替えと同じ記録（`TransitionKind::ProcessingChanged`、切り替えにかかった時間）を残す。フレームの欠けも重なりもない（テストで確認）。DoP の曲は切り替えない。
- **浮動小数点の曲を整数のデバイスで鳴らす**：MP3・AAC など浮動小数点の曲を、浮動小数点を受け付けないデバイスで鳴らすときは、音量 100% でも処理経路（段なし、TPDF ディザ）で整数にする（非可逆の曲には整数の原音がないため）。経路の記録には `processingRequired` を立てる。整数の曲をデバイスが受け付けない場合は、今までどおり変換せずに理由を出す（浮動小数点だけのデバイスなど）。2-3・2-4 で「M3 まで再生できない」としていたものが、これで鳴らせる。
- **判定の共通化**：直接送るか処理経路かの判定を `planPlayback()` にまとめ、`play()` と `ap_play --check` が同じものを使う。
- **表示**：経路の記録に `processingStages`・`processingRequired`・`dither` を足し、アプリ（ブリッジと画面の文言）と `ap_play` に出す（例：「あり（64bit 浮動小数点の処理経路：デジタル音量、TPDF ディザ）」）。`ap_play` に `--volume DB` と `--volume-at 秒:DB` を足した。
- **自動テスト**（完了条件）：
  - 100% で完全バイパス：受け入れテスト（3-1 の 72 通り）の処理の列に、0 dB の音量の段を入れても原音経路と一致する。Player でも音量 100% はビットパーフェクト。
  - ディザの統計：ディザの値が (−1, 1) の三角分布（分散 1/6、各区間の割合）。ディザをかけた量子化誤差は、入力が LSB のどこにあっても平均 0・分散 1/4 LSB²（ディザなしでは入力によって変わることも確かめる）。誤差は 1.5 LSB 以内。フルスケールでディザのせいで範囲の外と数えない。24bit（32bit コンテナ）では 24bit の LSB でかかり、下位 8 bit は 0。浮動小数点の出力にはかけない。同じ種なら同じ値。
  - 音量：0 dB だけ「何もしない」、出力を開いたときはその音量から、10 ms で直線的に移る（単調で、段差は1歩分以内、最後はちょうど目標値）、ミュート、0 dB に戻ったら移り終わってから「何もしない」。
  - Player：100% → −6 dB → 100% で「原音（16bit）→ 処理（32bit）→ 原音（16bit）」と開き直し、どのフレームも1回ずつ出る。浮動小数点の曲は、整数だけのデバイスでは 100% でも処理経路（ディザあり）、浮動小数点を受け付けるデバイスではビットパーフェクト。整数の曲でレートが合わないときは今までどおり断る。DoP の曲は音量を変えても切り替えない。
  - 3-1 のテストのうち「処理経路でも値が変わらない」ことを確かめていたものは、浮動小数点の出力（量子化しないのでディザもない）で完全一致、整数の出力では 1 LSB 以内、に書き換えた。MP3・AAC の「整数だけのデバイスでは断る」テストは「ディザをかけて整数にして鳴らす」に書き換えた。
- **要実機確認**（KA11 で、音量を下げてから）：
  1. MP3・AAC（`テスト用音源`）を `ap_play FILE --device N` で再生し、「処理：あり（…浮動小数点の曲を整数にする…TPDF ディザ）」と出て、普通に聞こえること（2-3・2-4 の実機での再生）。
  2. WAV か FLAC を `ap_play FILE --device N --volume-at 5:-12 --volume-at 10:0` で再生し、5 秒で音量が下がり（経路の切り替えの表示）、10 秒で元に戻る（原音経路に戻る表示）こと。切り替えのときに短い無音が入るのは仕様（約 25 ms と DAC がレートに合わせ直す時間）。途切れずに切り替えるのは 3-7。
- **実機確認（2026-11-10、FiiO KA11、排他 WASAPI）**：
  - MP3（`16-441-出力-Stereo-Out-convertio.mp3`、11 秒）：44.1 kHz の 32bit 整数で送り、「処理：あり（…浮動小数点の曲を整数にする…TPDF ディザ）」。普通に聞こえた（ユーザーが確認）。音切れ 0 回。2-3 の実機での再生はこれで完了。
  - WAV（16bit、11 秒）を `--volume-at 4:-12 --volume-at 8:0` で：0〜4 秒は原音経路（16bit そのまま）、4 秒で処理経路（32bit、デジタル音量・TPDF ディザ）、8 秒で原音経路に戻った。切り替えでデータが途切れたのは約 24 ms と 25 ms。音量の変化は聞こえたとおりで、切り替えのところも気にならなかった（ユーザーが確認）。音切れ 0 回。
  - AAC は `テスト用音源` になかった（.m4a はすべて ALAC）。iTunes で作った AAC を用意してもらい、元の WAV との比較（2-4 の残り）と一緒に確かめる。
